## 任務

盤點目前前端執行的運算邏輯，確認哪些結果會影響玩家資產、遊戲進度、隨機結果、獎勵或其他需要可信任的狀態，再規劃並逐步將這些權威運算移至後端。純顯示、動畫、介面互動及不影響權威狀態的呈現邏輯仍由前端處理。人類已確認採用雲端／離線雙模式：雲端登入模式的權威運算與狀態變更由伺服器執行；未登入時可離線遊玩。離線存檔與雲端存檔完全分開，使用不同資料識別與儲存區；登入後不接續、不匯入或同步離線遊戲進度及資產。依 OQ-15，登入時僅可沿用經確認不影響公平性的純個人設定。

### 全案執行順序（Owner 指定）

本任務依下列順序推進，不跳階段；前一階段完成必要決策與驗收後，才進入下一階段。各階段的 Board 子任務、驗收條件及相依關係須在拆分階段建立，不得以本任務中的規劃文字代替實際驗收。

1. **完成產品決策一致性檢查：** 核對 OQ-01～OQ-15，找出互相矛盾、定義不足或適用範圍不清的規則；先釐清必要的人類決策。
2. **設計雲端／離線存檔架構：** 納入多離線玩家槽位、帳號限定快取、登入／登出、資料承接邊界及失敗保護；遵守 OQ-04 完全分開保存與 OQ-15 純個人設定例外。
3. **設計伺服器權威架構：** 明確定義 RPC、資料表、權限、交易原子性、冪等性及隨機結果的責任歸屬。
4. **制定後端化優先順序：** 先處理模式與存檔隔離，再依序處理擲骰、資產交易、寵物、成就及排行榜。
5. **拆分 Board 子任務：** 每個階段建立獨立任務、明確驗收條件及相依關係，並遵守 Board 狀態規則。
6. **開始實作與測試：** 逐階段完成；核對後端部署、RPC 介面、權限及前端呼叫一致，完成隔離測試後才進入下一項。

**目前進度：** 第 1 階段 OQ-01～OQ-15 一致性檢查、第 2 階段雲端／離線存檔架構設計及第 3 階段伺服器權威架構設計已完成。現進入第 4 階段：依功能依賴、資產風險及部署門檻制定後端化優先順序；本階段只完成排序與驗收規劃，不代表資料庫或前端已實作、部署。

## 範圍與禁止

- 只動：本任務的盤點、設計與後續經確認的後端化實作，以及本任務必要的 board 紀錄。
- 不要動：未經盤點及確認，不得直接改寫前端或後端運算；不得假設所有純顯示、動畫或介面互動程式都必須搬到伺服器。
- 雲端模式：擲骰結果、資產增減、合成、出售、藥水、成就、每日任務、寵物、收益、天氣及排行榜權威資料，均由伺服器驗證、計算及寫入；前端只提交操作意圖並呈現伺服器結果。
- 離線模式：保留本機運算與本機存檔，並清楚標示為離線資料；不得將離線存檔直接上傳、合併或認列為雲端權威資產。若未來需要轉移，只能另訂明確的人工／伺服器驗證與轉移規則。
- 純顯示、動畫、通知、倒數呈現及介面互動可留在前端；其輸出不得成為雲端授權或資產變更的依據。
- 實作須檢查資料可信度、交易原子性、冪等性、授權、併發控制與 RPC 介面一致性。

- Migration CSV：`Supabase_State_2026-11-01_14-49_migration_versions.csv`；共 33 筆版本，最新為 `20261031165644 add_dice_grants_to_player_grants`。

### public schema 現況

- 23 張 public tables 全部啟用 RLS，但 `FORCE ROW LEVEL SECURITY` 均為 false；共有 36 筆 public RLS policies、498 筆 public table grants、80 筆 public function grants、67 筆 public constraints、33 個 public indexes。
- 重要資料表包含 `game_saves`、`player_profiles`、`player_grants`、`potion_usage_logs`、`craft_logs`、`pet_fusion_logs`、`pet_fusion_odds`、`realm_weather_state`、`realm_weather_contributions`、`player_weather_overrides`、`realm_global_boost`、`roll_announcements` 等。
- 已見政策方向：`game_saves` 允許登入者建立／讀取／更新自己的存檔；`player_grants` 僅有讀取自己的 grants policy；`potion_usage_logs` 允許玩家新增及讀取自己的紀錄；`player_profiles` 可公開讀取、登入者只能建立／更新自己的 profile。這些政策與 grants 仍需逐表逐欄核對，不能只憑「RLS 已啟用」判定安全。
- public schema 有 21 筆 function rows（含 `convert_weather_with_glove` 的兩個 overload），涵蓋管理員天氣／全域加成／寵物融合機率、天氣手套、天氣骰投入與召喚、手套購買、帳號裝置鎖、藥水更新及稽核觸發器等。
- public triggers 有 `player_profiles.trg_audit_player_profile_changes` 與 `realm_weather_state.realm_weather_history_trigger`；另外有 auth/storage/realtime 系統 triggers。需區分 trigger function 與可由前端直接呼叫的 RPC。

### 已發現的高風險後端項目

- `public.update_player_potions(target_user_id uuid, delta integer)` 為 `SECURITY DEFINER`，未設定固定 `search_path`；其定義直接依傳入的 `target_user_id` 鎖定並更新 `player_grants.potions`，沒有在函式內驗證 `auth.uid()` 與目標使用者是否一致，也沒有管理員授權檢查。
- 該函式 ACL 顯示 `PUBLIC`、`anon`、`authenticated`、`service_role` 均具有 `EXECUTE`。這是快照中優先級最高的安全疑點：具備呼叫權限者可能透過任意目標 UUID 與 delta 操作其他玩家藥水。尚未執行攻擊性測試，也未修改正式環境；應先確認實際前端呼叫者／用途，再設計安全替代 RPC、限制 EXECUTE、補足身份與數值驗證及交易測試。
- `SECURITY DEFINER` 函式中另有多個以 `auth.uid()`／JWT 管理員身份檢查的 RPC；部分使用 `search_path = public, pg_temp`，部分使用空 `search_path`。後續需逐一檢查所有者、ACL、固定 search_path、schema-qualified object references、呼叫者身份與資料列鎖定。
- `purchase_glove(p_glove_id text)` 為非 `SECURITY DEFINER`，函式內以 `auth.uid()` 限定玩家本人，並以單一 UPDATE 條件檢查金幣及是否已購買；`deposit_weather_dice`、`convert_weather_with_glove`、`summon_realm_weather` 為 `SECURITY DEFINER` 並有登入身份檢查與 `FOR UPDATE`／資料更新流程。仍須驗證 grants、前端參數與重複／併發行為。

### `update_player_potions` 安全處置

- CSV 顯示舊函式仍存在，為 `SECURITY DEFINER`，`search_path` 未固定；ACL 同時授予 `PUBLIC`、`anon`、`authenticated`、`service_role` 執行權限。函式接受任意 `target_user_id` 與 `delta`，沒有驗證呼叫者與目標玩家是否一致。
- 完整程式庫搜尋未找到任何現存呼叫點；`docs/board-readme-template` HEAD 的舊版單檔 `index.html` 也沒有呼叫此 RPC。T-0001 拆出的 `script.js` 改用 `claim_player_grants`、`craft_player_potion`、`use_player_potion`、`claim_achievement_potion`，不再使用舊 RPC。
- 新增獨立 migration：`supabase/migrations/20261101070948_remove_legacy_update_player_potions.sql`。若舊函式存在，先撤銷 `PUBLIC`、`anon`、`authenticated`、`service_role` 的全部權限，再不使用 `CASCADE` 刪除該函式；不依賴完整藥水庫存 migration，可獨立移除舊 RPC。
- 新增唯讀驗證 SQL：`supabase/tests/legacy_update_player_potions_security.sql`，確認 migration 後 `to_regprocedure(...)` 不再找到舊函式。
- **正式環境尚未修復。** 本次只建立本機 migration 與驗證 SQL，沒有執行正式 DDL。CSV 的 migration history 不包含 `20261028_authoritative_potion_inventory`，且 CSV 未找到 `claim_player_grants`、`craft_player_potion`、`use_player_potion`、`claim_achievement_potion` 等新 RPC；根目錄既有完整藥水 migration 的部署說明亦明載尚未套用 live Supabase。故不得把本機 SQL 當成已部署。
- 本機未安裝 `psql`，Docker Desktop daemon 目前未啟動；新增的 SQL 測試尚未在 PostgreSQL 隔離環境實際執行。正式套用前仍須備份、確認目標專案與 migration 流程，套用後執行驗證 SQL 並重新匯出 CSV。

### 前端權威邏輯初盤點（2026-11-01）

目前盤點對象為本分支 `script.js`（994 行；程式碼內容有長行壓縮格式）。依程式呼叫與狀態寫入位置，先分成以下項目；這是靜態程式碼盤點，尚未逐項追查所有資料表政策與後端函式定義。

| 項目 | 目前前端行為 | 權威性／風險 | 後端化方向 |
|---|---|---|---|
| 擲骰與機率（`weightedRoll`、`doRoll`） | 前端使用 `Math.random()`、權重與玩家加成計算結果，並直接更新 `S.bag`、`S.rolls`、`S.rollCounts`、`S.first`、藥水／寵物技能次數及每日統計 | **最高**。抽取結果、機率、公平性、資產入袋及消耗效果均可由玩家修改客戶端偽造 | 登入雲端模式由伺服器抽取並原子寫入；前端只呈現回傳結果。離線模式另定義本機規則及存檔標示 |

| 寵物出售／被動收益（`applyPetAutoSell`、`petIncome` interval、寵物出售 modal） | 前端計算稀有度售價、收益倍率及離線／在線收益，直接增加金幣 | **最高**。玩家可修改時間、收益率、倍率與出售結果 | 伺服器以持有寵物及伺服器時間計算收益；出售由伺服器驗證並原子更新 |
| 天氣骰投入／召喚／轉換 | 雲端路徑呼叫 `deposit_weather_dice`、`summon_realm_weather`、`convert_weather_with_glove`；但轉換候選天氣先在前端隨機選擇，本機模式直接改狀態 | **高**。雲端 RPC 已承擔部分交易，但本機分支及前端候選隨機仍需釐清；須核對 RPC 是否自行決定結果及檢查資產 | 讓後端決定天氣結果、消耗骰子／手套與期限；本機模式保留獨立離線模擬 |

### 雲端／離線模式隔離風險

- `save()` 在有 `currentUser` 時會排程 `syncCloudSave()`；`syncCloudSave()` 會將 `savePayload()` 整份寫入 `game_saves`，並將前端計算的擲骰數、收藏數、稀有度、金幣及成就統計寫入 `player_profiles`。
- `loadCloudSave()` 讀取雲端存檔時，會把本機寵物、已發現寵物、裝備寵物等資料與雲端資料合併；雲端尚無存檔時，會以 `localSaveBeforeCloud` 初始化狀態並呼叫 `syncCloudSave()`。這會讓既有離線存檔在首次登入時直接成為雲端資料，與本次確認的信任邊界衝突。
- `auth.onAuthStateChange` 設定 `currentUser` 後即呼叫 `loadCloudSave()`；目前未見獨立的離線／雲端模式狀態或存檔來源標記。
- 因此後續第一個實作階段應先建立明確模式與存檔來源隔離，停止登入時自動合併／上傳本機資產，並定義新帳號雲端初始化流程。既有玩家的首次遷移需另訂政策，不能默認把本機資料認列為可信資產。
- 上述結論來自 `script.js` 靜態呼叫路徑檢查；尚未以瀏覽器情境測試確認所有登入、登出、跨帳號及首次註冊流程。

### 建議後端化順序

1. **模式與存檔隔離**：先分離雲端權威資料與離線本機資料，移除登入時的本機資產合併／自動上傳，明確處理既有玩家遷移。
2. **擲骰核心交易**：伺服器決定隨機結果、套用加成、檢查背包容量、消耗一次性效果並原子新增骰子及統計；這是後續成就、任務及寵物事件的可信來源。
3. **資產交易**：骰子出售、背包擴充、手套購買／合成、藥水合成／使用及天氣骰投入／召喚／轉換，逐項建立伺服器端驗證與原子交易。

6. **排行榜與存檔收斂**：排行榜欄位改由伺服器交易維護；`game_saves` 僅保留非權威偏好／介面狀態，並核對 RLS、欄位 grants 及 RPC ACL。
7. **隔離驗收**：逐項涵蓋未登入／未授權、偽造數量與結果、重複請求、併發、交易失敗回滾、離線資料不得升格及跨帳號切換。

#### OQ-01：玩家是否可以不登入、完全以離線模式遊玩？

- **選項 A：可以。** 優點：保留單機遊玩及無網路可玩性；缺點：登入／離線入口、資料標示及功能限制需要額外設計。

#### OQ-02：玩家登入後，是否可以主動切回離線模式？

- **選項 A：可以明確切換。** 優點：玩家可選擇本機遊玩；缺點：介面必須清楚提示目前模式，避免誤以為離線進度會同步。
- **選項 B：登入後固定雲端模式。** 優點：降低模式混淆；缺點：登入玩家無法在雲端服務不可用時繼續離線遊玩，除非另行登出。
- **建議：A，但切換必須由玩家明確操作，不能自動切換或自動合併資料。**

#### OQ-03：雲端遊玩途中斷線時，系統應如何處理？

- **選項 A：停止雲端權威操作，等待連線恢復。** 優點：不會把未確認的本機結果當成雲端結果；缺點：短暫斷線會中斷遊戲操作。
- **選項 B：自動轉成離線模式。** 優點：遊戲不中斷；缺點：玩家可能誤認為離線操作已計入雲端，且必須處理兩套狀態並存。
- **選項 C：詢問玩家是否切換離線模式。** 優點：玩家有控制權；缺點：仍需清楚隔離雲端與離線狀態，且切回雲端時不得回灌離線資產。
- **建議：A 或 C；禁止 B 的無提示自動降級。**

#### OQ-04：離線存檔與雲端存檔是否要分開保存？

- **Owner 最終選 B：允許建立多個本機離線檔案／玩家槽位。** 這代表同一台裝置可保存多份彼此分開的離線進度；不代表允許多個雲端帳號共用資料，也不代表離線存檔可以直接轉成雲端資產。槽位如何建立、切換、命名及刪除仍需設計。

#### OQ-15 白話版：離線遊玩時的設定，登入後可不可以一起帶過去？

**決策邊界：** 僅純個人設定可沿用；此選擇不允許離線資產或遊戲進度直接變成雲端權威資料。

**Owner 最終選 B：** 登入時允許沿用不影響遊戲公平性的純個人設定，例如音量、畫面偏好及按鍵配置。骰子、金幣、寵物、藥水、成就、遊戲進度及排名等權威資料一律不屬於此轉移範圍；實際可轉移的設定欄位仍須在實作時逐項確認。

14. **雲端首次建立確認與既有帳號差異**：依 OQ-14，只有尚無雲端進度的帳號才顯示首次建立說明及確認；既有雲端存檔不得被當成新帳號重建，也不得因確認流程重置。COS 需提出可靠判斷條件及重試行為。

15. **載入／儲存失敗與中斷保護**：定義讀取失敗、寫入失敗、瀏覽器關閉、儲存空間不足及網路中斷的處理。雲端權威資料未載入成功時，依 OQ-12 鎖住會改變資產／進度的操作；離線資料寫入失敗時明確提示，避免顯示成功但未保存。

16. **純個人設定的來源優先順序**：定義離線設定、雲端帳號設定及預設值的讀取優先順序，以及何時寫回。建議雲端帳號已有設定時以帳號設定為準；僅缺少且在白名單內的欄位，才從離線設定補入一次，並記錄來源。

17. **模式與資料來源顯示**：依 OQ-13，定義常駐模式標示、目前槽位／帳號識別、存檔來源及儲存狀態提示。COS 提出 UI 位置與文案，不需要 Owner 決定技術實作。

18. **測試與驗收矩陣**：涵蓋多槽位互不覆蓋、匯入損壞檔、匯入失敗、刪除確認、帳號切換競態、登入登出、離線資料不得上雲、雲端載入失敗、儲存空間不足及個人設定白名單。由 COS 建立測試案例及通過條件。

**本階段交付方式：** Owner 已完成第 1～3 項產品政策確認（依序為 C、C、B）；第 4 項三項設定白名單由 COS 依遊戲功能與既有 OQ-15 決策處理。第 5～18 項由 COS 直接提出完整架構方案與驗收條件。Owner 不需要回答技術問題，也不必參與資料表、RPC 或瀏覽器儲存技術選型。COS 完成第 2 階段設計稿及風險檢查後，才進入第 3 階段。

### 第 2 階段：雲端／離線存檔架構設計稿（2026-11-01）

本節是依 Owner 已確認政策提出的技術設計基準。它完成第 2 階段的架構提案，不代表已建立資料表、RPC、前端模式切換或已部署任何內容。進入第 3 階段前，應以本節作為伺服器權威架構設計的輸入。

#### 1. 核心資料邊界

系統分成三個互相隔離的資料域：

| 資料域 | 保存內容 | 儲存位置 | 信任規則 |
|---|---|---|---|
| 離線玩家槽位 | 該槽位完整離線遊戲進度及其三項個人偏好 | 瀏覽器 IndexedDB | 完全由本機持有；匯入資料也永遠屬於離線資料，不得成為雲端資產或排行榜依據 |
| 雲端權威資料 | 骰子、金幣、藥水、手套、寵物、成就、任務、收益、天氣貢獻及其他遊戲權益 | Supabase，由伺服器端 RPC／資料庫交易維護 | 伺服器是唯一權威來源；瀏覽器快取只供畫面讀取，不能直接回寫權威欄位 |
| 雲端個人偏好與快取 | 已確認的三項個人偏好，以及依帳號取得的雲端資料唯讀快取 | Supabase 個人偏好資料及 IndexedDB 帳號分區 | 以 Supabase user ID 分區；快取不是權威資料，切換帳號時不得交叉使用 |

三個資料域不得共用同一份 `S` 物件作為可直接保存／同步的完整資料。前端可以在記憶體中組合畫面需要的狀態，但每一筆資料必須保留來源與模式；雲端模式下，會影響資產或進度的操作只能提交操作意圖，由伺服器回傳結果後更新畫面。

#### 2. 離線槽位與瀏覽器儲存

- **採用 IndexedDB。** 遊戲存檔包含骰子背包、寵物、成就及其他巢狀資料，LocalStorage 同步寫入容易阻塞主執行緒，也不適合承擔多槽位及原子替換。LocalStorage 僅保留 Supabase Auth SDK 所需的登入 session，以及少量非權威裝置識別／介面狀態；不得繼續把完整遊戲狀態寫入共用的 `diceRealmSave_v1`。
- 資料庫名稱建議 `diceRealmLocal`，初版 schema version 為 `1`。Object stores：`offlineSlots`（keyPath `slotId`，保存單一槽位資料與 metadata）、`appMeta`（保存目前選取的離線槽位 ID、格式遷移標記及本機資料庫版本）。雲端快取另使用 `cloudCache` store，key 必須包含 Supabase user ID 與資料類型；不得把雲端快取放入 `offlineSlots`。
- 每個離線槽位至少包含 `slotId`（由 `crypto.randomUUID()` 產生）、`displayName`、`createdAt`、`updatedAt`、`schemaVersion`、`gameState`、`personalSettings`。槽位 ID 是系統識別，不由匯入檔指定；顯示名稱可以重複，但列表必須同時顯示建立／更新時間以供辨識。
- 首次進入離線模式且沒有槽位時，自動建立一個「離線玩家 1」預設槽位。之後由玩家新增、命名及選取槽位。建議初版最多 20 個槽位；新增前檢查數量及儲存空間，超過上限時明確提示玩家先匯出或刪除單一槽位。
- 單一匯入檔上限建議 10 MiB。寫入前以 `navigator.storage.estimate()`（若瀏覽器支援）檢查可用空間，預留至少 20% 緩衝；此估算只作預警，實際寫入仍須捕捉 `QuotaExceededError`。所有新增、覆蓋及刪除使用 IndexedDB transaction；交易失敗時維持原槽位資料並顯示失敗原因。
- 離線槽位每次成功保存才更新 `updatedAt`。UI 顯示「離線模式／目前槽位名稱／已保存或保存失敗」；寫入尚未完成時不得顯示保存成功。瀏覽器關閉或頁面重新載入後，從 `appMeta` 讀取上次選取槽位；若槽位不存在，回到槽位選擇／建立流程。

#### 3. 舊版 LocalStorage 資料遷移

目前 `script.js` 的 `KEY='diceRealmSave_v1'` 同時被離線遊玩及雲端登入流程讀寫；`save()` 也會寫入 `KEY_user_<uid>`，而 `loadCloudSave()` 會合併本機寵物等資料，甚至在雲端沒有 `game_saves` 時把本機狀態上傳。因此舊 `KEY` 不能被直接認定為離線存檔，`KEY_user_<uid>` 也不能被當成可信雲端資產。

- 不得在登入事件、首次載入或背景工作中自動把舊 `KEY` 複製到雲端或新離線槽位。
- 首次啟用新版離線模式時，若偵測到舊 `KEY` 且沒有新離線槽位，顯示明確選項讓玩家檢視並選擇是否將這份「來源未能確認的舊本機資料」匯入為離線槽位。匯入前先驗證資料格式；成功寫入 IndexedDB 並重新讀回確認後，才寫入遷移完成標記。原始 LocalStorage 資料在過渡期保留，不自動刪除。
- 若玩家已登入雲端，舊 `KEY` 不得參與雲端初始化或雲端資料合併。既有 `game_saves` 由雲端讀取並保留；舊本機資料若要保存，只能透過明確的離線匯入流程建立獨立槽位。
- 舊版帳號快取 `KEY_user_<uid>` 只能作為非權威顯示快取的歷史資料。伺服器資料成功載入後可重新建立新版唯讀快取；不得將舊快取的資產欄位回傳伺服器。

#### 4. 匯出／匯入格式與資料驗證

- 建議副檔名 `.drsave`，內容為 UTF-8 JSON。Envelope 固定包含 `format: "dice-realm-offline-save"`、`formatVersion: 1`、`exportedAt`、`slot`、`gameState`、`personalSettings`。不包含 Supabase user ID、登入 session、雲端快取、裝置鎖 ID、管理員授權資訊或其他槽位資料。
- 匯出只接受玩家目前明確選取的一個槽位；匯出內容只包含該槽位遊戲資料及其純個人設定。檔案名稱可由槽位名稱與日期組成，但檔案內容不得把 email 或雲端身份當成槽位識別。
- 匯入先檢查檔案大小、JSON 可解析性、格式識別、版本、必要欄位、巢狀結構、型別、數值範圍、陣列長度、已知骰子／藥水 ID、背包及寵物上限，以及不允許欄位。未知版本、欄位型別錯誤、超出範圍或無法安全轉換時拒絕匯入，不猜測欄位意義。
- 匯入時忽略檔案內的 `slotId`、使用者 ID、來源宣告及時間戳作為本機身份依據；由本機重新產生 `slotId` 與 `createdAt`。所有匯入結果都標記為離線來源，即使檔案內容包含看似雲端的資料也不例外。
- 依 Owner 決策，匯入預設建立新槽位，也可選擇覆蓋既有單一槽位。覆蓋前顯示目標槽位名稱與更新時間並進行二次確認。先在暫存物件完成完整驗證，再以單一 IndexedDB transaction 原子替換；transaction 失敗時原槽位必須完整保留。
- 同名槽位允許存在；重複匯入視為新槽位，產生新的 ID，並提示玩家可能是相同內容。檔案中的名稱需去除控制字元、限制長度，空白名稱改用預設名稱。

#### 5. 刪除與資料保護

- 玩家只可刪除明確選定的單一離線槽位，不提供「清空全部槽位」按鈕。刪除前第一次確認顯示槽位名稱、最後更新時間及不可復原的後果；第二次確認提供「先匯出備份」及「不備份直接刪除」兩條路徑，符合 Owner 的 C 決策。
- 若選擇匯出，必須等匯出檔成功產生後才進入刪除確認；匯出失敗不得繼續刪除。若選擇不備份，仍需第二次明確確認。
- 刪除 transaction 只刪指定 `slotId`。若刪除的是目前槽位，成功後才切換至另一槽位；若沒有其他槽位，建立新的空白預設槽位。刪除失敗時維持原選取狀態並提示。
- 匯入覆蓋、槽位刪除及 schema migration 均需確保操作具原子性；不得以先刪除舊資料再寫入新資料的兩步驟流程實作。

#### 6. 雲端帳號資料與伺服器權威來源

- Supabase Auth session 只用來識別登入帳號。載入雲端模式時，以 session 的 `user.id` 作為帳號分區依據；不採信存檔 JSON 或匯入檔自帶的 user ID。
- `game_saves(user_id, save_data, updated_at)` 目前每個帳號只有一列 JSONB 存檔；`player_profiles` 目前包含 `coins`、`total_rolls`、`unique_dice`、`rarest_den`、成就數等統計欄位；`player_grants` 保存管理員發放的金幣、藥水及骰子累計值。這些是 2026-11-01 14:47 快照中的既有結構，不代表所有欄位目前都已具備伺服器權威寫入保護。
- 後續第 3 階段應逐步將權威資產及進度從客戶端可寫 JSON 拆出，由 RPC／資料庫交易維護。`game_saves` 過渡期間只允許保存明確列出的非權威偏好／介面狀態；不得再接受客戶端提交的骰子數量、金幣、藥水、寵物、成就、任務、抽取結果或統計作為可信更新。前端不得直接 upsert `player_profiles` 的權威統計欄位。
- 新增獨立的 `player_preferences`（建議）保存三項允許沿用的個人設定；以 `user_id` 作為主鍵並外鍵關聯 `auth.users`。欄位建議為 `auto_sell_dice_ids text[]`、`potion_auto_add_ids text[]`、`weather_auto_add_enabled boolean`、`weather_auto_add_dice_ids text[]`、`updated_at timestamptz`。所有欄位都必須由伺服器白名單驗證 ID、數量及型別；RLS 限本人讀取，寫入透過以 `auth.uid()` 為唯一身份來源的 RPC。若第 3 階段發現既有偏好資料模型更合適，可調整實際 schema，但不得把偏好塞回權威資產 JSON。
- 目前程式實際可確認的偏好欄位：背包自動出售清單為 `autoDeleteDice`；藥水自動添加清單為 `potions.autoAddPotions`，`potions.autoAdd` 是依清單推導的開關；天氣自動投入設定為 `autoDepositWeatherEnabled` 與 `autoDepositDice`。`autoSellThreshold` 及 `autoDepositThreshold` 雖存在於舊資料預設／保存流程，但目前搜尋未找到實際操作邏輯，因此不納入跨模式沿用白名單；`potions.materials` 是材料數量，絕不可當成偏好轉移。
- 雲端快取以 `cloudCache:<userId>:<resource>` 分區。只在伺服器成功回應後更新快取，並記錄 `fetchedAt`、資料版本及來源；快取不可直接送回伺服器。快取過期或載入失敗時，可選擇顯示明確標記為過期的唯讀畫面，但所有權威操作必須鎖定。

#### 7. 登入、登出及帳號切換狀態流程

前端使用明確模式狀態，建議至少包含 `booting`、`offline_slot_select`、`offline_loading`、`offline_ready`、`cloud_authenticating`、`cloud_loading`、`cloud_ready`、`cloud_readonly_error`、`signing_out`。模式狀態不得只由 `currentUser` 是否為空推斷。

| 事件 | 必須執行的處理 | 完成後狀態 |
|---|---|---|
| 首次啟動且未登入 | 開啟離線槽位資料庫；選取上次槽位，沒有槽位則建立預設槽位 | `offline_ready` |
| 玩家登入 | 先暫停離線寫入及計時器；只擷取目前槽位的三項允許偏好到記憶體；清空離線遊戲狀態；建立新的 auth generation；取得帳號裝置鎖後向伺服器讀取雲端 bootstrap 狀態 | `cloud_loading` |
| 既有雲端帳號 | 讀取既有雲端權威資料及偏好；不合併任何離線資產；只有雲端偏好欄位缺少時，才以一次性流程補入目前離線槽位的對應偏好 | `cloud_ready` |
| 尚無雲端進度 | 顯示 OQ-14 首次建立說明並要求確認；確認後由伺服器原子建立初始雲端資料；取消則不建立、不上傳離線資料，維持登入流程受限並提供登出選項 | 確認後 `cloud_ready`；取消後維持受限登入狀態直到登出 |
| 雲端讀取／bootstrap 失敗 | 不使用離線資產替代、不自動切換離線模式；顯示錯誤與重試／登出入口；可顯示明確標記過期的帳號快取作唯讀參考 | `cloud_readonly_error` |
| 登出 | 停止雲端操作與計時器、取消待執行同步、釋放裝置鎖、使舊請求 generation 失效、清除記憶體中的帳號資料，再載入目前離線槽位 | `offline_ready` |
| 切換雲端帳號 | 先完整執行登出清理，再對新帳號執行登入流程；不得沿用上一帳號記憶體狀態或快取 | `cloud_loading` 後依結果轉換 |

每個非同步請求開始時記錄 `authGeneration` 與 `userId`；回應套用前再次確認兩者仍相同。帳號切換、登出或重新登入時遞增 generation，使舊請求結果失效，避免慢速回應覆蓋新帳號畫面。雲端模式登入後固定留在雲端模式；斷線只會進入唯讀／等待狀態，不得自動降級成離線模式。

#### 8. 首次雲端建立與既有雲端帳號判斷

- 不得只用 `game_saves` 是否存在作為「新帳號」唯一判斷，因為帳號可能已存在 `player_profiles`、`player_grants`、天氣貢獻或其他雲端紀錄。
- 第 3 階段建議提供單一伺服器 bootstrap RPC，依 `auth.uid()` 在同一交易中檢查雲端帳號資料，回傳明確狀態：`existing`、`new_requires_confirmation`、`incomplete_or_conflict`。此 RPC 不接受客戶端傳入目標 user ID。
- `existing` 必須保留既有雲端資料並進入逐步權威化流程，不顯示新帳號確認、不重置存檔。`new_requires_confirmation` 才顯示 OQ-14 說明；使用者確認後呼叫獨立初始化 RPC，該 RPC 再次檢查資料並以唯一約束／交易避免重複建立。若確認期間其他請求已建立資料，應回傳 `existing` 而不是覆蓋。
- `incomplete_or_conflict` 代表資料表存在部分紀錄但不足以安全判斷，不自動建立或清除任何資料；停止權威操作並回報需要後端核對。這可保護既有玩家及歷史資料。
- 首次建立只建立雲端初始狀態與雲端偏好預設值；不讀取 `diceRealmSave_v1`、離線槽位或匯入檔中的資產、進度及身份資訊。

#### 9. 三項個人偏好的沿用規則

| 偏好 | 離線欄位 | 雲端偏好欄位 | 沿用條件 |
|---|---|---|---|
| 擲骰背包自動出售清單 | `autoDeleteDice` | `auto_sell_dice_ids` | 雲端欄位尚未設定時，才從目前選取的離線槽位補入一次 |
| 藥水材料自動添加選擇 | `potions.autoAddPotions`（`autoAdd` 由清單推導） | `potion_auto_add_ids` | 只搬移藥水種類選擇，不搬移材料數量、藥水庫存或效果 |
| 天氣召喚自動添加清單 | `autoDepositWeatherEnabled`、`autoDepositDice` | `weather_auto_add_enabled`、`weather_auto_add_dice_ids` | 只搬移啟用狀態及選擇清單，不搬移天氣結果、貢獻點數或骰子資產 |

偏好沿用只發生於登入時、使用者已選定目前離線槽位且雲端偏好缺少對應欄位的情況。雲端已有值時一律優先採雲端值；成功寫入雲端後記錄來源與完成狀態，避免每次登入重複覆蓋。雲端使用者後續修改偏好只更新雲端偏好；登出後離線槽位仍保留原本設定，不反向同步雲端值。三項設定的驗證必須採骰子／藥水 ID 白名單及目前遊戲資料定義，不得讓偏好值直接執行資產變更。

#### 10. 失敗保護與交易要求

- **離線保存失敗：** IndexedDB transaction 未完成前不更新 UI 為已保存；失敗時保留記憶體中的待保存狀態、提示玩家匯出／重試，不能靜默重置或改寫其他槽位。
- **匯入失敗：** 驗證階段不碰現有槽位；transaction 失敗回滾；原槽位內容及目前選取槽位不變。
- **雲端載入失敗：** 依 OQ-12 鎖定資產／進度操作，不將快取或離線狀態當成伺服器結果，不排隊補送離線操作。
- **雲端寫入失敗／逾時：** 前端不得先樂觀增加資產；保留操作失敗狀態，重試時使用同一 idempotency key。若逾時但伺服器可能已提交，先查詢該操作結果或由伺服器以冪等鍵回傳原結果，不能直接再執行一次。
- **帳號切換競態：** 每次登入／登出更新 generation；所有讀取、偏好補入、裝置鎖 heartbeat 及操作回應都必須確認 user ID 與 generation。舊帳號回應不得更新新帳號 UI 或 cache。
- **瀏覽器儲存空間不足：** 預先估算並處理 quota error；不自動刪除舊槽位，不覆蓋玩家其他槽位；提供匯出與手動刪除單一槽位的入口。
- **頁面關閉／中斷：** IndexedDB transaction 保證單筆寫入原子性；雲端交易由資料庫確保原子性。前端不得把尚未收到伺服器確認的操作標記成功。

#### 11. 模式與資料來源 UI

- 遊戲主畫面固定顯示醒目的「離線模式」或「雲端模式」。離線模式另顯示目前槽位名稱；雲端模式顯示帳號識別（以安全的顯示名稱為主）及雲端連線／唯讀錯誤狀態。
- 存檔區顯示資料來源、最近成功保存時間及保存狀態。雲端快取若過期，明確標示「快取資料／唯讀」；離線匯入後顯示「匯入的離線存檔」。
- 登入流程在切換前說明離線進度不會帶入雲端；首次雲端建立依 OQ-14 顯示確認。離線槽位管理提供新增、命名、選取、匯出、匯入、刪除；雲端帳號頁不提供離線槽位刪除或匯入雲端的操作。
- 雲端斷線時保持雲端模式標示，顯示「雲端連線中斷，權威操作已暫停」及重試／登出入口，不顯示離線模式，也不把操作切換成本機計算。

#### 3. 權威資料模型

**3.1 `player_game_state`：每位玩家唯一的權威遊戲狀態**

建議新增資料表，採 `user_id uuid PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE`，另設 `state jsonb NOT NULL`、`state_version bigint NOT NULL DEFAULT 1`、`schema_version integer NOT NULL`、`last_income_at timestamptz`、`created_at`、`updated_at`。`state` 必須是 JSON object，並由伺服器驗證固定 schema、型別、數值上下限及允許的 ID。

`state` 的權威內容包括：

- 骰子背包數量、首次取得紀錄、擲骰總數與各骰統計、最佳紀錄、背包容量。
- 金幣、手套持有與裝備狀態。
- 藥水庫存、材料數量、啟用中的效果、剩餘次數及伺服器計算的到期時間。
- 寵物個體、唯一 pet UID、變異、重量、裝備 UID、技能次數及伺服器收益累積基準。
- 成就解鎖、獎勵領取狀態、每日任務進度及每日獎勵狀態。
- 其他會影響抽取結果、資產、獎勵、遊戲進度或排行榜的伺服器狀態。

不得放入離線槽位資料、雲端快取副本、客戶端自報的排行榜統計或純個人設定。單一玩家的資產交易都先對該玩家的 `player_game_state` 列執行 `SELECT ... FOR UPDATE`，再驗證、計算及更新；所有修改同一玩家狀態的 RPC 因此會依資料列鎖序列化。JSONB 聚合是第一階段的相容性方案，後續若查詢量或資料成長證明有必要，再將骰子／寵物等子集合正規化成獨立資料表，不在初次導入時同時大幅改寫所有資料結構。

**3.2 `player_preferences`：三項純個人設定**

建議獨立保存，欄位只包含目前白名單：`auto_delete_dice text[]`、`potion_auto_add_enabled boolean`、`potion_auto_add_ids text[]`、`weather_auto_deposit_enabled boolean`、`weather_auto_deposit_dice text[]`，另有 `user_id`、`updated_at`。這些欄位分別對應擲骰背包自動出售清單、藥水材料自動添加設定、天氣召喚自動添加清單。每次更新都驗證 ID 是否屬於正確類別與允許範圍；偏好只決定玩家希望系統如何處理，不提供任何資產或權限。雲端已有值時優先使用雲端值，僅缺少欄位時才依第 2 階段政策補入一次。

**3.3 `player_action_requests`：操作冪等紀錄**

建議欄位：`user_id uuid`、`request_id uuid`、`action_type text`、`request_hash text`、`response jsonb`、`created_at`、`completed_at`，主鍵為 `(user_id, request_id)`。同一帳號同一 request ID 只能代表同一種操作與同一份輸入；相同 ID 搭配不同內容必須拒絕。回傳結果在交易內保存，供逾時重試取回原結果。

**3.4 `player_game_events`：權威事件紀錄**

建議新增 append-only 事件表，保存 `event_id`、`user_id`、`request_id`、`event_type`、`payload jsonb`、`created_at`。用於擲骰結果、資產增減、合成、藥水使用、寵物生成／出售、成就及任務獎勵等追蹤。事件由 RPC 在同一交易寫入；玩家不可直接 insert、update 或 delete。事件紀錄供稽核與重建核對使用，不接受客戶端提供的結果作為事實。

| 資料表 | 第 3 階段後的責任 |

#### 4. RPC 契約與責任分工

所有玩家 RPC 從 JWT 的 `auth.uid()` 取得玩家身份，不接受 `target_user_id`、`user_id` 或其他可指定受益人的客戶端參數。所有會改變資產／進度的操作均帶 `p_request_id uuid`。以下是建議介面名稱與語意；實作時仍須以實際 SQL signature、PostgREST 參數名稱及前端呼叫逐字核對。

| RPC | 建議輸入 | 伺服器責任／回傳 |
|---|---|---|
| `get_player_bootstrap()` | 無 | 依登入者載入權威狀態、偏好、profile 及 `state_version`；回傳 `ready`、`needs_initialization_confirmation`、`legacy_pending_review` 或 `migration_required` 等狀態，不讀取離線槽位。 |
| `initialize_player_cloud_state(p_request_id, p_confirmed)` | 操作 ID、玩家已完成首次建立確認 | 僅在帳號尚無雲端權威狀態且確認有效時建立初始狀態；不得讀取或接收離線遊戲進度。重複請求回傳同一結果。 |
| `roll_dice(p_request_id)` | 操作 ID | 伺服器讀取天氣、加成、藥水、寵物技能及權威骰池；決定單次結果、消耗效果、套用自動出售／材料保留／天氣投入偏好、更新背包與統計、檢查成就及每日任務，最後回傳結果與新版本。前端不得傳骰子 ID、結果、機率、運氣值或玩家擲骰總數。 |
| `sell_player_dice(p_request_id, p_dice_id, p_quantity)` | 操作 ID、骰子 ID、數量 | 驗證持有量、出售資格及伺服器售價／倍率，原子扣除骰子並增加金幣及任務進度。前端不得傳售價或金幣差額。 |
| `upgrade_player_bag(p_request_id)` | 操作 ID | 伺服器決定下一級容量及價格，檢查金幣與容量上限後原子扣款、升級。 |
| `purchase_glove(p_request_id, p_glove_id)`、`craft_glove(p_request_id, p_glove_id)` | 操作 ID、商品／配方 ID | 伺服器讀取價格或配方、檢查金幣／材料／持有狀態，更新裝備及相關成就獎勵。舊 `purchase_glove(p_glove_id)` signature 在新前端完成切換及相容性驗證後退場。 |
| `craft_player_potion(p_request_id, p_potion_id)`、`use_player_potion(p_request_id, p_potion_id)` | 操作 ID、藥水 ID | 伺服器讀取配方、材料與庫存，驗證並原子扣除／增加；啟用效果與到期時間由伺服器決定。不可接受客戶端傳入材料數量、效果期限或獎勵內容。 |
| `deposit_weather_dice(p_request_id, p_dice_id, p_quantity)` | 操作 ID、骰子 ID、數量 | 驗證骰子屬於可投入類別、持有數量及投入上限；同交易扣除骰子並更新 `realm_weather_contributions`。舊兩參數 signature 待前端切換後撤除。 |
| `summon_realm_weather(p_request_id)` | 操作 ID | 鎖定玩家權威狀態與全域天氣列，驗證點數及特殊天氣限制，由伺服器決定天氣並扣除點數，更新天氣狀態與歷史。 |
| `convert_weather_with_glove(p_request_id, p_scope)` | 操作 ID、影響範圍 | 驗證手套持有／裝備、冷卻及全域／個人範圍，伺服器決定天氣結果並原子更新玩家狀態與天氣資料。現有無參數及 `p_scope` overload 必須先盤點 ACL 與呼叫者，再決定保留單一 signature；不可讓模糊 overload 長期並存。 |
| `fuse_player_pets(p_request_id, p_pet_uids, p_tier)` | 操作 ID、玩家選擇的寵物 UID 與合成級別 | 驗證 UID 全部屬於呼叫者、材料／條件及機率設定；伺服器決定合成結果、變異與重量，原子消耗材料並建立新寵物及紀錄。不得接收客戶端指定的稀有度、結果、重量或隨機種子。 |
| `set_player_pet_equipment(p_request_id, p_pet_uids)` | 操作 ID、裝備 UID 清單 | 驗證持有權、重複 UID 及裝備數量上限，更新裝備狀態。 |

| `claim_daily_reward(p_request_id)` | 操作 ID | 只依伺服器事件累積的當日任務進度判定是否完成；透過唯一領取紀錄確保每天只發放一次。 |
| `update_player_preferences(...)` | 僅三項白名單設定欄位 | 驗證設定 ID 與數量上限後更新偏好；不得接受遊戲資產、效果、統計或進度欄位。 |
| `set_player_username(p_username)` | 玩家名稱 | 伺服器正規化名稱、檢查唯一性及長度後更新 profile；不允許同時更新排行榜統計。 |

所有 mutation RPC 使用一致回傳 envelope：`ok`、`request_id`、`state_version`、`result`、`events`、必要的 `error_code`。Bootstrap 才回傳完整狀態；一般操作優先回傳最小結果及必要 state delta，避免每次傳送整份權威存檔。客戶端只能用回傳資料更新畫面，並忽略比目前畫面 `state_version` 更舊的延遲回應。

#### 5. 交易原子性、冪等與併發規則

每個 mutation RPC 必須在單一 PostgreSQL transaction 內完成下列流程：

1. 取得 `auth.uid()`；未登入立即拒絕。驗證 request ID、參數型別、允許 ID、數量及上限。
2. 以 `(user_id, request_id)` 建立冪等紀錄。若已存在，鎖定並比較 `action_type` 與 `request_hash`；完全相同且已完成則直接回傳原本 `response`，內容不同則拒絕。並行相同請求由唯一鍵衝突等待前一交易完成，再讀取已保存結果。
3. 對 `player_game_state` 執行 `SELECT ... FOR UPDATE`；需要全域天氣時，依固定順序再鎖定 `realm_weather_state`，避免不同 RPC 以相反順序取得鎖造成死鎖。
4. 只讀取資料庫中的資產、配方、價格、機率、效果及時間；伺服器驗證操作前置條件並計算所有變化。不得採用客戶端提交的結果或舊快取。
5. 在同一交易更新權威狀態、profile 投影、grant claim、天氣貢獻／狀態、唯一獎勵紀錄及 append-only 事件；保存冪等回應與新 `state_version`。
6. 全部成功才 commit。任一條件失敗即 rollback，不能留下「扣了材料但沒產生物品」、「發了獎勵但未記錄領取」或「擲骰結果已顯示但資產未保存」等半套狀態。

同一 request ID 重試必須回傳同一結果，不能再次扣款、擲骰、發放或消耗效果；同一 ID 改參數必須拒絕。不同 request ID 的同玩家操作透過狀態列鎖依序執行；跨玩家的全域天氣操作另鎖定全域狀態。客戶端逾時後不得自行回復本機資產或另造新 request ID 盲目重送；應以原 ID 查詢／重試，並等待伺服器結果。

#### 6. 隨機結果與時間責任

- 雲端擲骰、寵物生成、變異、重量、天氣召喚／轉換、寵物技能觸發及其他隨機獎勵，全部由伺服器決定。前端 `Math.random()` 只可用於動畫、裝飾及純視覺效果；不得影響雲端狀態。
- 快照確認 `pgcrypto` 1.3 位於 `extensions` schema。雲端隨機抽樣採伺服器密碼學隨機位元（例如 `extensions.gen_random_bytes()`）搭配無偏差抽樣；不可將目前 `summon_realm_weather()` 的 `random()` 或前端 `Math.random()` 視為公平性基礎。隨機抽樣 helper 不得暴露給客戶端作為可選種子介面。
- 骰池、骰子資料、權重、天堂藥水機率表、天氣修正、寵物個體權重、寵物變異率、重量分布、配方、價格、背包容量與收益規則必須由伺服器端版本化設定提供。前端可保留同一份靜態資料作圖示及說明，但伺服器不信任客戶端傳回的資料。
- 所有冷卻、效果到期、每日重置、被動收益與活動時間以資料庫 `now()`／`clock_timestamp()` 為準。前端時間只負責顯示倒數；寵物收益由 `last_income_at` 計算，需設定單次可累積上限，避免改系統時間或長期離線造成無上限收益。
- 伺服器應在事件紀錄中保存結果 ID、使用的規則版本、必要的機率／加成快照及伺服器時間，以便事後核對；不需要向玩家揭露隱藏機率表。

#### 7. 權限、RLS 與函式安全基準

- `player_game_state`、`player_action_requests`、`player_game_events` 的 INSERT／UPDATE／DELETE 權限不得授予 `anon` 或 `authenticated`；事件與冪等紀錄也不得由玩家直接讀取其他帳號。讀取權限只透過驗證 `auth.uid()` 的 bootstrap RPC 提供必要資料。
- `game_saves` 完成新狀態讀寫切換後，撤銷 `authenticated` 對 `save_data` 的直接 INSERT／UPDATE；保留必要的唯讀／管理核對權限。`player_profiles` 撤除玩家對統計欄位的直接寫入；若需欄位級授權，必須確認 column grants 不會繞過預期限制。更名改走 `set_player_username`。
- `player_grants` 玩家保留必要的唯讀權限；發放資料的建立、領取標記及轉入權威狀態只能由可信管理後端／伺服器交易完成。前端不得把 `adminGrantApplied` 或任何 localStorage 欄位當成已領取證據。
- 所有玩家 mutation RPC 預設採 `SECURITY DEFINER` 搭配嚴格身份驗證及最小 ACL，或採 `SECURITY INVOKER` 且只給足夠的欄位權限；每個函式必須明確選擇並說明理由。若採 `SECURITY DEFINER`，必須設定 `search_path = ''`、所有資料表與函式使用 schema-qualified 名稱、驗證 `auth.uid()`、限制 EXECUTE 給 `authenticated`，並撤銷 `PUBLIC`／`anon` 的執行權限。管理員 RPC 另驗證伺服器端管理員角色，不依賴前端 `isAdmin()` 或只靠可變更的畫面狀態。
- 每個既有及新增 overload 都要逐一核對完整 signature、owner、`SECURITY DEFINER`、`search_path`、函式內容與 ACL。不能只看函式名稱，也不能只因資料表啟用 RLS 就判定安全。現有天氣 RPC 的 `public, pg_temp` search_path、管理員 email 判斷、`get_weather_dice_exist_counts()` 的可執行角色及兩個 `convert_weather_with_glove` overload，均列為切換前必查項目。
- `service_role` key 僅留在受信任伺服器環境，不進入 GitHub Pages、前端 bundle、localStorage 或公開設定。公開前端只持有 Supabase anon/publishable key，並受 JWT、RPC ACL、RLS 與函式內部授權限制。

#### 8. 既有雲端資料與舊 RPC 過渡策略

- 遵守 OQ-07：保留既有 `game_saves`，逐帳號接管；未核對的資產暫不視為可信。不得把所有舊 JSONB 一次複製到 `player_game_state` 後就標記可信，也不得直接清空或重置既有玩家資料。
- 每個既有帳號先由伺服器 bootstrap 判定 `legacy_pending_review`。舊存檔保留原始副本與雜湊／時間等核對資訊；只有經規則驗證、資料一致性檢查及必要人工確認的欄位，才可寫入新權威狀態。未核對的資產可以保留供顯示／查核，但不得出售、消耗、合成、領獎或列入權威排行榜。哪些舊欄位能自動驗證，依後續遷移工具與實際資料分布制定，不從本次 22 筆存檔列數推定所有資料均可信。
- 新帳號依 OQ-14 先顯示首次建立雲端進度的確認，再呼叫 `initialize_player_cloud_state`。初始化只建立伺服器預設狀態，不接受離線存檔或任何客戶端資產快照。既有帳號不得誤走新帳號初始化流程。
- 既有 `purchase_glove`、`deposit_weather_dice`、`summon_realm_weather`、`convert_weather_with_glove` 逐一建立新權威版本；前端切換完成、正式 RPC 已部署且 ACL／隔離測試通過後，才撤除舊 signature。未部署的藥水 RPC（`claim_player_grants`、`craft_player_potion`、`use_player_potion`、`claim_achievement_potion`）不得先被前端當成可用介面；需先完成其定義、測試與部署核對。
- `player_grants` 的累積值需設計一次性轉入流程，為每筆舊發放建立可追蹤 grant ID 或可信基準值；同一筆 grant 不得因重新登入、快取清除或重試重複入帳。新管理員發放從導入後直接寫入權威狀態或唯一 grant ledger。
- 新舊前端切換需有明確版本門檻。先部署資料表、RPC、ACL 與測試，再部署前端；確認新版前端不再呼叫舊直接寫入路徑後，才撤銷舊 table grants／RLS write policies 及退場舊 RPC。不可先撤權限造成現行線上版本立即失效，也不可先發布依賴尚未部署 RPC 的前端。

#### 9. 第 3 階段驗收矩陣

| 編號 | 情境 | 驗收結果 |
|---|---|---|
| S3-01 | 未登入呼叫任一玩家 mutation RPC | 拒絕；不建立或修改任何玩家資料 |
| S3-02 | 使用者 A 傳入使用者 B 的 UUID 或試圖指定 B 為受益人 | 介面不接受 user ID；函式只依 `auth.uid()` 操作 A |
| S3-03 | authenticated 直接 INSERT／UPDATE／DELETE 權威狀態、冪等紀錄或事件 | 權限拒絕；不能繞過 RPC |
| S3-04 | 玩家直接修改 `game_saves.save_data` 或 profile 統計欄位 | 新版切換後權限拒絕；舊版相容期間明確標示尚未完成撤權 |
| S3-05 | 相同 request ID、相同參數重送 | 回傳第一次保存的結果；資產與事件只變更一次 |
| S3-06 | 相同 request ID、不同參數重送 | 拒絕；不產生第二次狀態變更 |
| S3-07 | 兩個不同 request ID 同時出售同一批骰子 | 由列鎖序列化；不得超賣，餘額不足的交易完整 rollback |

| S3-09 | 客戶端偽造骰子 ID、數量、價格、機率、金幣或寵物結果 | 伺服器只接受允許的操作意圖，依權威資料重新驗證及計算 |
| S3-10 | 客戶端改系統時間或提交 pet income elapsed | 伺服器忽略客戶端時間，使用資料庫時間及收益上限 |
| S3-11 | 相同玩家同時進行擲骰、出售、合成及藥水使用 | 依固定鎖定順序序列化；每次結果反映最新已提交狀態 |
| S3-12 | 多玩家同時召喚／轉換全服天氣 | 玩家資產列及全域天氣列鎖定順序一致；不重複扣點或覆蓋未完成交易 |
| S3-13 | 擲骰／寵物／天氣隨機操作 | 結果由伺服器密碼學隨機來源產生；前端不能指定結果或種子 |
| S3-14 | 透過 localStorage 修改 `adminGrantApplied` 或清除快取 | 不會重複領取或憑空取得管理員發放資產 |
| S3-15 | 直接 insert 偽造 `roll_announcements`／craft／potion／pet logs | 權限拒絕；可信紀錄由 RPC 同交易建立 |
| S3-16 | 舊帳號含未核對 `game_saves` | 保留原始資料並標記待核對；未核對資產不進入權威交易或排行榜 |
| S3-17 | 新帳號首次建立雲端狀態 | 必須先完成 OQ-14 確認；初始化不讀取離線資產 |
| S3-18 | A 帳號請求延遲後切換 B 帳號 | 前端以帳號世代／state version 隔離回應；A 的結果不得覆寫 B 畫面或快取 |
| S3-19 | RPC 使用 `SECURITY DEFINER` | 固定空 search_path、schema-qualified、檢查呼叫者及 ACL；PUBLIC／anon 無 EXECUTE |
| S3-20 | 舊 RPC overload 或直接寫入路徑仍存在 | 切換前盤點並逐一驗證；不得留下可繞過新權威狀態的舊入口 |

#### 10. 本階段交付結論與後續階段入口

第 3 階段採用「每玩家一份伺服器權威狀態＋獨立偏好＋冪等請求紀錄＋不可由玩家寫入的事件紀錄」作為第一版架構。所有資產、隨機結果、時間、成就及任務進度由資料庫交易決定；玩家身份只取自 JWT；所有會改變狀態的操作都在單一交易內鎖定、驗證、更新及保存結果。`game_saves` 與 `player_profiles` 的舊直接寫入通道必須在前端完成切換後撤除。

第 3 階段完成後，依 Owner 指定順序進入第 4 階段「制定後端化優先順序」：以模式／存檔隔離為先，接著擲骰核心、資產交易、寵物、成就／每日任務、排行榜與資料收斂；第 5 階段再建立各自 Board 子任務及相依關係。第 3 階段不建立新 migration、不修改現有 RPC、不調整正式 RLS／grants，也不部署前端或後端。

### 第 4 階段：後端化優先順序與交付依賴（2026-11-01）

本階段依 Owner 指定的「模式／存檔隔離 → 擲骰 → 資產交易 → 寵物 → 成就／每日任務 → 排行榜」順序，結合第三階段權威資料模型及 `script.js` 實際呼叫路徑，整理成可拆分的實作批次。排序同時區分開發先後與正式切換門檻：開發可以分批進行，但任何雲端功能只有在其完整依賴已部署、權限與隔離測試通過、前端不再走舊寫入路徑後，才可切換給玩家使用。

#### 1. 排序依據

1. **信任邊界優先：** 先確立雲端／離線模式、身份、bootstrap、資料來源及快取隔離，避免新 RPC 仍讀取或覆寫不可信的舊存檔。
2. **核心資產風險優先：** 擲骰結果會直接決定骰子資產、統計、效果消耗與後續事件，是所有遊戲經濟及進度的主要事件來源。
3. **依賴完整性優先：** 擲骰會讀取天氣、手套、藥水及寵物被動效果；擲骰 RPC 必須在同一權威狀態下取得這些效果並處理一次性消耗。相關狀態讀取／消耗能力屬擲骰上線前置條件，即使該系統完整管理介面排在後續批次。
4. **獎勵來源優先：** 成就及每日任務必須依可信事件計算；排行榜必須依伺服器維護的統計投影產生，不能先把舊 profile 數字當成可信資料。
5. **切換風險優先：** 每批先部署資料結構、RPC、ACL、測試及相容層，再切換前端；所有舊寫入路徑都要在確認線上前端不再使用後才撤權。

#### 3. 批次內的實作順序與邊界

**P0：先建立可安全進入雲端模式的入口。** 先實作離線槽位及舊 LocalStorage 的明確匯入流程，再實作雲端帳號分區快取、bootstrap、首次初始化與登入／登出／切帳狀態機。`save()` 不再同時寫入離線資料、雲端快取及權威資料；雲端模式只將伺服器回傳狀態放入唯讀快取。偏好只允許 `auto_delete_dice`、藥水材料自動添加及天氣召喚自動添加三項白名單。此批完成前，不啟用任何雲端權威操作。

**P1：擲骰必須是一個完整的伺服器交易。** 現有 `doRoll()` 在瀏覽器增加擲骰次數、呼叫 `weightedRoll()`，再自行扣除天使藥水／寵物技能次數、計算額外金幣、處理材料保留、自動出售、背包入袋、首次發現、最佳紀錄及任務進度。這些步驟必須合併到 `roll_dice(p_request_id)`，不能只把隨機抽樣搬走而把其餘資產變更留在前端。伺服器須讀取當下有效天氣、手套、藥水及已核對寵物效果，並在同一交易消耗一次性效果、更新骰子資產及寫入事件。前端動畫時間、骰面呈現、音效、結果文字及自動連擲排程仍可留在瀏覽器。

P1 的自動處理也必須遵守三項偏好：自動出售只改變伺服器處理本次擲骰產物的方式；藥水材料自動添加只保留符合配方且未超過材料容量的產物；天氣骰自動添加必須在同一交易內驗證並記錄天氣貢獻。偏好不能讓玩家持有不存在的骰子，也不能讓背包容量、出售價格或天氣點數由客戶端決定。

**P2：依交易依賴拆成可獨立驗收的子批次。** 建議順序為：出售／背包擴充 → 手套購買／合成／裝備 → 藥水合成／使用 → 天氣投入／召喚／轉換 → grant 領取。藥水啟用、天氣狀態及手套效果雖列在 P2 完整管理，P1 開始雲端擲骰前必須已具備可被伺服器安全讀取與消耗的權威狀態；因此這些必要的最小 RPC／資料欄位須提前完成，或與 P1 同批交付。不得讓雲端擲骰忽略玩家已持有的有效效果。

**P3：先讓寵物成為可信資產，再開放完整寵物玩法。** P1 需要讀取已核對寵物的被動加成及技能計數；P3 再完成合成、變異、重量、裝備、自動出售及收益全流程。寵物合成使用的骰子、隨機結果及新寵物 UID 必須由伺服器產生；被動收益以資料庫時間及 `last_income_at` 計算，不再採用前端每秒累加 `petIncomePending`。舊寵物在核對前可保留原始資料供顯示，但不得提供權威加成、出售或收益。

**P4：以事件作為唯一進度來源。** P1～P3 的交易在同一交易內寫入可信事件；成就與每日任務只消費這些事件或權威狀態。先完成條件／進度計算，再完成獎勵領取與唯一性保護；避免先遷移前端 `checkAchievements()`，卻仍依賴可由客戶端偽造的 `S.rolls`、`S.bag` 或 `S.coins`。

**P5：最後建立可信公開視圖。** 排行榜、玩家統計、稀有公告及歷史紀錄都從權威狀態或伺服器事件產生。玩家名稱更新可獨立使用驗證過的 RPC；`last_seen`／在線狀態屬輔助資料，不得反向更新權威資產。舊 `player_profiles` 統計在確認來源前只能標示為歷史／待核對資料。

**P6：完成資料收斂及舊入口退場。** 逐帳號處理舊存檔與 grant，保留原始資料、核對摘要及轉換結果；再確認目前正式前端不再呼叫舊 `game_saves`／`player_profiles` 直接寫入、舊 RPC signature 或舊 overload。最後才撤銷相應 grants／policies／函式。每次正式環境變更都須由具備權限的 Owner／管理者依核對後 SQL 執行，並以新的唯讀快照驗證。

#### 5. 正式切換的共同門檻

- 新資料表、函式、參數、回傳 envelope、RLS、table grants、function ACL、trigger 及 overload 均已核對；正式環境部署狀態以新的唯讀快照為準。
- RPC 已在目標 Supabase 專案部署，且完成未登入、跨帳號、偽造參數、資源不足、重複 request ID、相同 ID 不同參數、併發交易及 rollback 測試。
- 前端已改為傳送操作意圖並使用伺服器回傳結果；不存在同一操作同時更新本機權威狀態及呼叫 RPC 的雙重入帳路徑。
- 已確認 GitHub Pages 實際載入的前端檔案與版本。`script.js` 的本機內容不能推定為線上版本；目前既有紀錄指出線上 HTML 尚未切換至拆分後的 `script.js`，正式切換前必須重新核對。
- 有明確的舊版相容與回復方案；新前端依賴的 RPC 必須先部署，舊權限撤除則必須等新前端完成切換並確認不再使用後才執行。
- 正式環境 DDL／DML、RLS／grants 變更及部署由具備權限的 Owner／管理者執行；本專案對話使用者不是該 Supabase 專案 Owner，COS 只能準備經核對的 SQL 與驗證步驟。
