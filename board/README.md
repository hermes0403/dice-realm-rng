# Board — 多方 AI／人類協作任務板

本文件是 `board/` 的**唯一流程規範**。本專案使用四個固定角色：棒子、叉子、barry、老查。專案安全、Git、Supabase 與執行環境規範見根目錄 `AGENTS.md`。

## 1. 核心原則與角色

### 1.1 四個固定角色

| 角色 | 所屬權限群組 | 定義 |
|---|---|---|
| `棒子` | `owner_side` | dice-realm-rng 遊戲最高 Owner，擁有最終決策權 |
| `叉子` | `owner_side` | 棒子的 GPT；僅在棒子授權範圍內代理及執行 |
| `barry` | `collaborator_side` | 棒子的協作者，即本專案使用者 |
| `老查` | `collaborator_side` | barry 的 GPT，即 COS／本對話助理 |

角色前綴是任務紀錄的作者／權限標記，不是工具名稱。COS 即老查的執行環境；不得因使用其他工具而自動取得棒子或 barry 的身份及權限。棒子保留最高決策權；叉子不得冒充棒子本人或自行擴張授權。

### 1.2 權限隔離矩陣

任務的 `from` 決定該任務的權限歸屬；`to`、`owner`、`contributors` 或執行分支均不能改變任務歸屬。`棒子`／`叉子` 屬棒子方；`barry`／`老查` 屬協作者方。`done` 只能由人類決定；GPT 不得自行決定。人類在對話中明確表示結案決定後，同方 GPT 可依 §8 的代記格式代為登記；沒有明確人類決定及可回查來源，不得標記 `done`。

| 任務由誰開立 | 可正常變更該任務狀態、送審及驗收者 |
|---|---|
| `barry` 或 `老查` | 一般狀態操作由 barry、老查依授權辦理；涉及棒子最終決策時仍須棒子確認；`done` 僅由 barry 決定，老查可依 §8 代記 |
| `棒子` 或 `叉子` | 一般狀態操作由棒子、叉子依授權辦理；叉子不得超出棒子授權，棒子保留最終決策權；`done` 僅由棒子決定，叉子可依 §8 代記 |

棒子方適用部分（包含棒子／叉子的權限操作、任務分支及 PR 流程、原有叉子整合預先授權的調整）待棒子本人確認；確認前不得將本文件對棒子方新增或變更的限制視為已獲棒子同意。

- barry 可以驗收老查開立的協作者方任務；棒子可以驗收叉子開立的棒子方任務。
- barry／老查 **不得**變更、送審或驗收棒子／叉子開立的任務；叉子不得變更、送審或驗收 barry／老查開立的任務。
- GPT 只能代表所屬一方行事，不得冒充另一方；不得自行作出 `done` 驗收決定。人類明確決定後，同方 GPT 可依 §8 代記，`done_by` 仍填作出決定的人類。棒子保留最高 Owner 最終決策權。
- `review` 與 `done` 同樣受此權限隔離；不得以「只是送審」、「只是退回」或「只是填完工欄位」為由繞過限制。
- 任務指派給誰、誰實際寫程式、誰是 `owner`、誰提交 commit，都不會轉移任務開立方的狀態權限。

### 1.3 明確授權

- 跨方共同工作不會自動改變任務歸屬。若需讓另一方代為執行特定狀態操作，必須由原權限方明確記錄任務 ID、允許動作、代理角色及有效範圍。
- GPT 不得代替所屬人類作出未被明確授權的人類決策；尤其不得自行宣稱棒子已同意、驗收或放棄最高 Owner 權限。

### 1.4 需要 Owner 權限驗證的任務

- 若驗收必須使用只有棒子方持有的管理員帳號、Owner 權限或正式環境操作權限，該工作一律由棒子方開立 owner_side 任務，交由 `叉子` 實作，並由 `棒子` 親自驗收。
- 此類任務的 `from` 必須是實際開單的 `棒子` 或 `叉子`，`to`／`owner` 指派 `叉子`，`reviewer`／`done_by` 指定 `棒子`。叉子不得自行代替棒子做最終驗收。
- barry／老查可以提出需求、整理驗收步驟、提供一般帳號可取得的證據及建立協作者方的前置任務；不得代替棒子／叉子建立 owner_side 任務、變更其狀態或代替棒子驗收。需要此類工作時，應請棒子方建立任務並提供任務 ID。
- 若協作者方任務的完成依賴上述 Owner 權限驗證，應記錄對應 owner_side 任務 ID，並維持 `blocked`，直到 owner_side 任務完成且棒子確認驗證結果。

## 2. 任務檔案與編號

- 一個任務一個檔案，檔名：`T-<4位數編號>-<英文短名>.md`，例如 `T-0009-potion-rpc-review.md`。
- 範本：`board/_TEMPLATE.md`。
- 最小任務 ID 固定為 `T-0001`。新編號使用 `board/` 根目錄及 `board/archive/` 中已存在的最大編號 + 1。建立前先檢查，避免撞號。任務編號撞號依 §12「公開」定義處理：撞號雙方中尚未公開者，改用下一個可用編號並在紀錄說明；若雙方都已公開（已推送分支、已建立 PR 或已合併），任何一方都不得自行改號，停手回報，由 barry 或棒子逐案授權。推送任務分支或建立 PR 之前，必須再次檢查遠端分支與 PR 是否已有同一 ID。
- 一張任務應有單一、可驗收的主要目標。大型工作拆成多張任務，以 `depends_on` 連結。
- 任務建立後不可因為執行者或分支改變而重新指定 `from`；若任務歸屬填錯，應由原開單方留下更正紀錄，跨方代理另依第 1.3 節明確授權。
- 通過驗收並結案後，將任務檔移至 `board/archive/`；不可刪除任務歷史。`AGENTS.md`、`board/README.md`、`board/_TEMPLATE.md` 是永久規範文件，不得歸檔。

## 3. Frontmatter 欄位

所有任務 frontmatter 都必須包含下列全部欄位，欄位順序依範本；一行一個 `key: value`，避免多行 YAML 值，以便工具掃描。尚未指派的單值欄位保留空值，清單欄位使用 `[]`，不得省略欄位或自行改用舊值。

| 欄位 | 定義 |
|---|---|
| `id` | 唯一任務 ID，例如 `T-0009` |
| `title` | 任務標題 |
| `status` | 任務目前狀態，依第 4 節 |
| `from` | **開單來源／權限歸屬**，只能是 `棒子`、`叉子`、`barry`、`老查` |
| `to` | 被交辦的對象；可為上述四個角色之一或 `any`，不影響 `from` 權限歸屬 |
| `owner` | 目前對交付負責的主要執行者；不可藉此改變任務權限歸屬 |
| `contributors` | 協作者清單；協助者不因此取得狀態變更權 |
| `reviewer` | 預定驗收者；仍須符合 `from` 權限群組或明確授權 |
| `priority` | `P0`、`P1`、`P2`、`P3` |
| `created` | 任務建立日期 |
| `updated` | 最近一次有效紀錄或狀態變更日期 |
| `depends_on` | 前置任務 ID 清單；未完成的依賴不得視為已解除 |
| `branch` | 主要執行者實際使用的個人分支；多人協作時以各自分支工作，並在紀錄補充其他分支 |
| `done_by` | 有權驗收並實際將任務標記為 `done` 的角色；不是單純提交成果者 |
| `done_at` | 正式驗收結案日期；只有狀態確實改為 `done` 時填寫 |

`from`、`to`、`owner`、`reviewer`、`done_by` 使用四個固定角色名稱。工具名稱可作為補充資訊，但不得取代角色前綴。

新舊任務一律使用 `P0`、`P1`、`P2`、`P3` 優先度；舊任務若仍使用 `high`／`normal`／`low`，更新時依原意分別轉為 `P1`／`P2`／`P3`。`reviewer` 未決定前留空；棒子方 Owner 權限任務依 §1.4 指定 `棒子`。

## 4. 狀態定義與轉換

| 狀態 | 意義 | 一般可執行者 |
|---|---|---|
| `open` | 已建立，尚未正式接手 | 開單方可建立；任務所屬權限群組可接手；communicate task 接收方依 §15.9 可接手該委派單 |
| `in_progress` | 已接手並正在執行 | 任務所屬權限群組；communicate task 接收方另依 §15.9 取得單張委派單的有限操作權 |
| `blocked` | 有明確阻礙，暫時無法繼續 | 任務所屬權限群組；communicate task 接收方另依 §15.9 取得單張委派單的有限操作權 |
| `review` | 執行成果已提交，等待有權限的一方驗收 | 任務所屬權限群組，或經原權限方明確授權的代理者 |
| `returned` | `communicate task` 接收方已完成自己負責的部分，正式交回原需求方確認；不代表原任務完成 | 接收方依委派授權提交；原需求方確認接回或要求補正 |
| `done` | 已由任務所屬方的人類正式驗收結案 | 協作者方僅 barry；棒子方僅棒子。GPT 不得代替人類決定或標記 `done` |
| `cancelled` | 經有權限者決定終止，不再執行 | 任務所屬權限群組，或經原權限方明確授權的代理者；communicate task 原需求方依 §15.9 確認該委派單取消處置 |

### 4.1 狀態轉換條件

- `open` → `in_progress`：接手者先確認沒有 `communicate task` 鎖定，並重新檢查五單容量閘門及 Communicate 優先閘門；兩者都未阻擋才新增接手紀錄，更新 `owner`、`branch`、`updated` 與 `status`。若有鎖定或任一閘門觸發，保持 `open`。
- `in_progress` → `blocked`：記錄阻礙內容、等待對象、需要的條件及下一步；阻礙解除後由任務所屬權限群組恢復 `in_progress`。
- `in_progress` → `review`：任務要求的成果已完成，驗收條件均有可檢查證據，且完工回報已填妥。若任務包含部署，必須實際部署至指定目標環境；純文件或不需部署的任務，以其驗收條件為準。只有本機完成、測試通過或準備部署，不得假稱已部署。
- `review` → `in_progress`：驗收未通過，由有權限的驗收方記錄未通過項目及原因，再退回執行。跨方協作者不得代替任務所屬方退回。
- `in_progress` → `returned`：**僅限具有完整 `## 委派資訊` 區塊的 communicate task**。接收方完成委派範圍後，填妥交付物、驗證證據及未完成事項，再依委派授權交回原需求方；`returned` 不等於 `done`。
- `returned` → `done`：原需求方的人類確認接回、交付符合要求，並完成原任務解鎖後，才可將 communicate task 結案；`done_by` 填該人類角色，並新增含「驗收」字樣及非空內容的驗收紀錄。人類明確決定後，同方 GPT 可依 §8 代記，不得自行決定。
- `returned` → `in_progress`：原需求方確認交付不完整，記錄具體差異及補正要求後，將委派單交回接收方繼續處理；原任務維持鎖定。
- `review` → `done`：驗收條件全部通過後，只能由任務所屬方的人類決定結案（協作者方為 barry；棒子方為棒子）；人類在對話中明確表示後，可由同方 GPT 依 §8 代記。`done_by` 填作出決定的人類角色、`done_at` 填結案日期，並新增含「驗收」字樣、非空 `來源：` 及可回查 `證據：` 的驗收紀錄。GPT 不得自行決定。
- `done` → `in_progress`：只有任務所屬方的人類可決定重開（協作者方為 barry；棒子方為棒子）。先將任務檔從 `board/archive/` 移回 `board/`，同步更新 Board 索引，再新增重開原因及人類決策紀錄，更新 `status`、`updated`，清空目前 frontmatter 的 `done_by`／`done_at`；原結案紀錄及其驗收資訊必須保留，不得刪改。重開後依一般規則重新執行，並重新檢查五單容量閘門及 Communicate 優先閘門；任一閘門為阻擋或 `UNKNOWN` 時，不得開始其他實作工作。
- `open`／`in_progress`／`blocked` → `cancelled`：有權限者明確決定取消，必須記錄原因、決策者及日期。若日後重新啟動，建立新任務並連結原任務，不直接抹除取消歷史。
- 狀態改變時必須同時新增紀錄並更新 `updated`。不得只改 frontmatter 而不留原因。

### 4.2 跨方影響註記（純通知）

- 任何角色發現成果可能影響另一方任務時，可以追加 `[impact][角色]` 紀錄；第二個中括號必須是實際添加紀錄的四個角色之一，例如 `[impact][老查]`。不得改寫或刪除既有紀錄。
- 當影響來源任務由 `in_progress` 轉為 `review`，或發現其他任務可能受到影響時，來源方的 GPT（棒子方為 `叉子`、barry 方為 `老查`）檢查變更內容及可能受影響任務，並追加 `[impact][GPT角色]` 紀錄。紀錄包含來源任務 ID、變更摘要、受影響範圍、需要對方知悉的事項及判斷理由。
- `impact` **只通知，不派工作、不建立待辦、不追蹤進度、不要求對方執行，也不改變任何任務狀態**。不得藉 impact 將 `open` 喚醒為 `in_progress`，也不得將「請處理」寫在 impact 後期待對方自動接手。
- 若確實需要另一方調查、修改、驗證、提供資料或作出其權限內決定，必須依 §15.9 建立正式 `communicate task`；任務 ID 可在 impact 中作為通知連結。
- impact 添加者不得藉通知接手實作、送審、退回、取消或驗收受影響任務；後續工作由任務原權限方或正式 communicate task 的明確授權處理。

## 5. 優先度

| 優先度 | 定義 | 判斷標準 |
|---|---|---|
| `P0` | 緊急 | 正式環境重大故障、資料安全／完整性風險，需立即處理 |
| `P1` | 高 | 核心功能不可用、重要交付被阻斷，應優先安排 |
| `P2` | 一般 | 正常功能開發、整合、錯誤修正或必要維護 |
| `P3` | 低 | 非必要改善、文件潤飾、低影響重構或待辦想法 |

優先度與狀態互相獨立；例如 `P0` 任務仍可能因等待正式 Owner 授權而處於 `blocked`。不得單純因任務已等待很久就自動升級優先度，調整時應新增紀錄及理由。

## 6. 開工與接續 SOP

每位協作者每次開啟新對話，依序讀取 `AGENTS.md`、本文件及相關任務全文，再依 §15 執行八階段生命週期。第一階段未達 `READY`，不得進入接手或開發；既有任務走第二階段後進第四階段，新需求走第三階段後進第四階段。每次 `open` → `in_progress` 前都必須重新檢查五單容量閘門及 Communicate 優先閘門。開工回報列出角色、權限群組、branch／工作環境、同步狀態、任務 ID、閘門結果及本次範圍。

## 7. 共同基準指標、任務分支與多人協作

- `work/barry`、`work/laocha`、`work/bangzi`、`work/chazi` 都是共同基準的同步指標：同步完成後必須與 `origin/main` 指向同一個 commit、不得領先，且必須能以 `--ff-only` 安全同步；不得在 `work/<role>` 上實作、累積新任務提交或把它當成任務分支來源。角色分支單純落後時，以 `git merge --ff-only origin/main` 同步；若 `--ff-only` 失敗，立即停止並回報，不得 reset 或改寫歷史。
- **過渡條款：**`work/laocha`、`work/chazi` 目前含有尚未進入 `main` 的提交。在逐任務抽出並確認保存前，不得刪除、重置、改寫這兩條分支，也不得將其作為任何新任務來源。檢查時標示 `KNOWN_DIVERGED`，並記錄獨有提交；此已知過渡狀態不視為違規。
- **棒子方確認狀態：**本節對棒子方（叉子）的新流程限制，以及原有「task branch → `work/chazi`」七條件整合預先授權的調整，均標示「棒子方適用部分待棒子確認」。棒子本人確認前，不得宣稱已取得棒子同意或由老查代替棒子撤銷／修改既有授權；新舊規則衝突時，叉子相關整合先停止並交棒子決定。
- **每張任務建立唯一短期任務分支**，命名為 `task/T-xxxx-short-name`，一律從建立當下的 `origin/main` 建立。任務分支只承載該任務的修改；不得從 `work/<role>`、其他任務分支或未同步的本機 `main` 建立。
- 同一任務的「開單 PR」、「開工 PR」及「交付 PR」三個階段，都使用同一條 `task/T-xxxx-short-name` 作為 PR head，PR base 一律為 `main`，合併方式一律為 GitHub merge commit。各階段 PR 合併後，先 fetch，再將同一任務分支以 `--ff-only` 同步至最新 `origin/main`，再繼續下一階段；不得另建分支承接同一任務。
- 任務 `branch` 欄位記錄唯一的 `task/T-xxxx-short-name`。開單與開工階段的 Board 提交，可使用只含 `board/` 變更的臨時 Worktree；推送後即移除。這種臨時 Worktree 不得承載程式實作或其他非 Board 變更。**正式任務 Worktree 必須等任務正式由 `open` 轉為 `in_progress`，且開工 PR 已合併後才建立**；任務仍為 `open` 時不得開始實作。
- 本規則自生效後的新任務開始適用；既有任務的 `branch` 欄位是歷史紀錄，不為符合新命名而回溯改寫。
- 預設每位協作者同時只執行一張需要寫入的任務；確有平行工作需求時，才為不同任務各自建立獨立 task branch/worktree，並先確認不會同時修改相同檔案或產生整合衝突。
- 任務分支若落後最新 `origin/main`，先 fetch，再在任務分支執行 `git merge origin/main` 更新基準；不得 rebase。若合併有衝突或無法確認安全，停止並回報。每次 PR 合併後以 `git merge --ff-only origin/main` 同步任務分支；若 `--ff-only` 失敗，立即停止並回報，不得 reset、強制同步或改寫歷史。
- 任務完成並通過驗證後，透過同一任務分支的交付 PR 合併至 `main`；不得先整合回 `work/<role>`。PR 建立、合併及 push 仍須符合 `AGENTS.md` 與本次明確授權；任何階段均不得把角色分支當作 PR head。
- 一人一支角色分支與一任務一支短期分支只規範 Git 隔離，不改變 Board 權限。Git 寫入能力與任務狀態權限是兩件事；合併分支不等於授予送審、退回或驗收權。
- 任務狀態更新只有在變更已整合到共同可見的 `origin/main` 後，才視為所有協作者都已同步看見。尚未整合的狀態須標示「分支內更新，尚未同步」，不得假設其他人已知悉。
- 同一任務多人協作時，指定一位主要 `owner` 對交付負責，其餘列入 `contributors`；不得使用多人共同 owner 模糊責任。

## 8. 紀錄格式與完工回報

- 「紀錄」只增不改；不得刪除或改寫任何人的既有紀錄。
- 一般格式：`- YYYY-MM-DD HH:MM [棒子|叉子|barry|老查] 內容`。代記格式：`- YYYY-MM-DD HH:MM [代記:<人類>/<代記者>] 內容｜來源：<人類原話與時間，或連結>`。人類限 `barry`、`棒子`；代記者限同一方 GPT（`barry` → `老查`、`棒子` → `叉子`）。人類必須先在對話中明確表示決定；代記者只能忠實登記，不得補造或推定決定。前綴規則同時允許四個角色前綴及上述合法代記前綴。每筆新紀錄都必須包含完整日期及時間（台灣本機時間，至少精確到分鐘），不得只寫日期、只寫時間或使用「剛剛／稍早」等相對時間；無法取得時間時先暫停新增紀錄，不得猜測。此新紀錄規則自 2026-11-11 起算，既有紀錄不回溯改寫。
- 跨方影響格式：`- YYYY-MM-DD HH:MM [impact][棒子|叉子|barry|老查] 內容`。`[impact]` 必須在角色前綴之前，第二組中括號記錄實際添加者。
- Communicate 鎖定紀錄依 §15.9 使用 `- YYYY-MM-DD HH:MM [角色] [COMMUNICATE_LOCK] task=T-xxxx actor=角色 at=YYYY-MM-DD HH:MM`；解除紀錄使用相同格式但標記為 `[COMMUNICATE_UNLOCK]`。`task=` 指向 communicate task ID，必須寫在其關聯原任務的紀錄中。
- 時間使用本機台灣時間；所有新紀錄均須有完整日期與時間，既有紀錄不回溯補寫或改寫。代記紀錄的 `來源：` 必須是人類原話及其時間，或可回查的原話連結；不得以 GPT 自己的摘要當成授權來源。
- 每次狀態轉換都要在同一任務新增紀錄，說明操作者、原因、前後狀態及必要證據。
- `done` 前必須先有一筆驗收紀錄：內容必須明確包含「驗收」二字，並分別提供非空的 `來源：` 與 `證據：`。`來源：` 記錄人類作出決定的原話及時間，或原話連結；`證據：` 記錄實際檢查的檔案、commit、測試結果或其他可回查技術證據。不得混用兩欄、只寫「通過」或留空。紀錄可由同方 GPT 依合法代記格式登記，但 `done_by` 仍填作出決定的人類角色。
- **代記抽查提醒（待 M2 實作）：**若代記者同時是任務 `owner`，且代記內容包含「驗收」或「授權」，validator 應提示人類抽查來源與原話；目前尚未實作，不得宣稱 validator 已檢查。
- `review` 前必須填完工回報：
  1. **改了什麼**：檔案清單、主要差異及相關 commit。
  2. **怎麼驗證的**：實際命令、exit code、測試或部署證據；未執行寫「未驗證」。
  3. **沒做／做不到的**：列出未完成項目及限制。
  4. **衍生任務／影響任務**：列出新任務 ID，或已追加 `[impact]` 紀錄的任務 ID。
- `done_by` 只填真正作出結案決定的人類角色（協作者方 `barry`、棒子方 `棒子`），不得填 GPT、工具名稱或單純提交成果者。`done_at` 記錄正式結案日期。
- 對話即將結束或工作者即將交接時，先新增進度紀錄，說明已完成、未完成、目前分支及下一步。

## 9. 依賴、阻塞與取消

- `depends_on` 中的任務尚未 `done` 時，依賴任務不得宣稱前置條件已完成；可以先做不依賴該項的部分，但必須記錄範圍。
- 原任務若有尚未解除的 `[COMMUNICATE_LOCK]`，即使 `depends_on` 已完成也視為工作鎖定：不得接手、啟動、修改實作或重複委派。只有原需求方確認接回後，才能新增對應 `[COMMUNICATE_UNLOCK]`；不得只刪除鎖定紀錄。
- `blocked` 必須寫清楚阻礙、等待誰、等待什麼、解除條件及下一個檢查點；不能把一般待辦或尚未開始直接標成 blocked。
- `cancelled` 必須有任務所屬權限群組或經原權限方明確授權代理者的決策紀錄及取消原因。取消不等於刪除。
- 任務重新啟動時建立新任務，`depends_on` 或紀錄連回原任務；不得刪除原任務歷史。

## 13. Branch／Worktree 管理

- 專案根目錄本身就是主要工作目錄，不另建長期角色 Worktree；若該工作目錄檢出 `work/<role>`，該分支僅作為 `origin/main` 的同步檢出，不在其中實作或累積任務提交。同步完成後必須與 `origin/main` 相同、不得領先，且必須可 `--ff-only` 同步。現存 `work/laocha`、`work/chazi` 的已知分歧依 §7 過渡條款標示 `KNOWN_DIVERGED`；逐任務抽出前不得刪除、重置、改寫或作為任務來源。
- 每張任務只建立一條 `task/T-xxxx-short-name` 分支，從 `origin/main` 建立。開單／開工階段可使用只含 `board/` 變更的臨時 Worktree 提交 Board 紀錄，推送後即移除；正式任務 Worktree 必須等任務狀態正式轉為 `in_progress` 且開工 PR 合併後才建立。建議正式 Worktree 路徑 `.worktrees/task-T-xxxx-short-name`。
- 標準任務分支可在開單階段建立，不需每次額外徵求建立同意：Board 任務已由有權限者建立／指派，且名稱與來源符合本節規範時即可建立。若要建立額外長期分支、非標準命名、跨任務分支或實驗性工作環境，老查須取得 Barry 明確同意，叉子須取得棒子明確同意。
- 開始 Worktree 工作前，確認任務已是 `in_progress`、任務分支源自 `origin/main`，且沒有其他執行者、未保存成果或來源不明修改。不得把其他任務的修改帶入本任務。
- 每次接續專案時列出 local branches、worktree 路徑及用途。發現用途不明的分支／worktree，先查明，不得自行刪除或改寫。
- 同一任務的開單 PR、開工 PR、交付 PR 都沿用同一任務分支；各 PR 以任務分支為 head、`main` 為 base，使用 merge commit。每次 PR 合併後 fetch，並以 `--ff-only` 將任務分支同步至最新 `origin/main`，不得改用另一條分支。
- 第七階段正式結案及 Board 任務紀錄交付完成前，不得清理該任務的 Worktree／短期分支；內容 PR 已合併但任務尚未驗收，不構成清理授權。結案後清理前，仍須確認 tracked／untracked 狀態、未提交修改、未追蹤檔案及分支是否仍承載其他成果。
- 若短期 worktree 有未提交修改或未追蹤檔案，不得強制移除；先列出並分類，經任務負責人決定保留或丟棄後再處理。不得因清理而刪除唯一一份 migration、測試、SQL、Board 紀錄或其他重要資料。
- 不得清理或改寫 `work/<role>`、`main` 的共同基準資料，或其他仍承載未完成任務的分支。`main` 不應作為日常實作 Worktree。

## 15. 八階段任務生命週期

本節是老查／Barry 與叉子／棒子雙方共同遵守的正式流程。兩方使用相同的判斷標準、權限隔離、證據要求及停止條件；只有本機 Git／Worktree 與 GitHub App 線上工作環境的實際操作方式不同。不得只執行方便的階段，也不得用建立分支、Worktree 或 App 工作環境繞過任何准入限制。

### 15.1 全階段共同規則

- 每個階段先完成所有安全可行的檢查，再集中整理缺漏、異常及人類決策事項，最後一次提出完整清單並暫停。若單一操作可能覆蓋資料、破壞歷史或造成不可逆影響，立即停止該項操作，但繼續其他不受影響的唯讀檢查。
- 老查與叉子都必須遵守上述順序。老查檢查本機 Repository／Worktree；叉子檢查 GitHub Repository、GitHub App 工作環境及其可取得的提交／PR 證據，不得要求叉子提供不存在的 Barry 本機路徑或 upstream。
- 人類決策題使用國中程度白話；技術術語第一次出現時立即用生活化例子解釋其意思及影響。每個決策獨立一題 A／B／C／D／E；E 永遠是「其他做法（請自行描述）」。有可靠建議時放在 A，標示建議方及理由；其他選項說明結果與代價。沒有可靠建議時中立列出優缺點，不硬推方案。每題說明現況、決策原因及選擇後驗證方式。
- 缺少資訊時，先自行完成可查的部分；記錄已知事實、未知內容、影響、可否安全繼續及需要誰提供什麼。不得把未執行的檢查描述為通過。
- 每次規範修改後，執行 `node scripts/validate-board.mjs`；需要檢查特定一方的即時容量時，另執行 `node scripts/validate-board.mjs --side=collaborator_side` 或 `--side=owner_side`。這項檢查只讀取 Board 任務檔，不會替人類作出接手決定。M1 新增的容量資料來源、Communicate 觸發條件、任務分支／PR 關係、Worktree 建立時點、公開 ID 固定、時間戳與人類驗收紀錄等自動檢查，均**待 M2 實作**；本文件不得宣稱目前 validator 已檢查這些新規則。

### 15.2 第一階段：工作環境准入

- **目的：**確認角色、Repository、工作環境、分支及提交關係正確安全，並判斷是否具備開始任務的條件。
- **檢查：**確認 AI 代表角色及權限群組；確認本機或 GitHub App Repository；確認目前 branch、HEAD SHA、`origin/main`、`work/<role>` 的同步狀態、任務分支及其建立來源；檢查提交差異、ahead／behind、merge-base、獨有提交、工作區修改、staged／untracked 檔案及其他執行者。
- **老查：**執行 `git fetch origin`，確認 `origin/main`。若目前檢出 `work/laocha`，正常同步後必須與 `origin/main` 相同、不得領先，並可 `--ff-only` 同步；已知未抽出的歷史提交依過渡條款標示 `KNOWN_DIVERGED`，不得拿來建立任務。專案根目錄仍是主要工作目錄，不另建長期角色 Worktree。列出 `git worktree list --porcelain`、`git branch -vv` 及目前工作區狀態。
- **叉子：**以 GitHub 線上 Repository 為權威來源，檢查 `main`、`work/chazi` 的同步狀態、task branch、commit compare／PR head/base 及 GitHub App 自身工作環境。已知未抽出的歷史提交依過渡條款標示 `KNOWN_DIVERGED`，不視為違規且不得作為任務來源。若 App 無法顯示未提交狀態，明確記錄限制，不得推定沒有未保存成果。棒子方適用部分待棒子確認。
- **提交關係判斷：**`SYNCED`、`BEHIND`、`AHEAD`、`DIVERGED`、`KNOWN_DIVERGED`、`UNKNOWN`。正常同步後必須 `SYNCED`，不得 `AHEAD`；落後時可安全 `--ff-only` 才能同步。已知過渡分歧標示 `KNOWN_DIVERGED`，不視為違規。不得丟棄提交、改寫歷史、強制 push 或直接選 ours／theirs。
- **結果：**`READY`、`BLOCKED` 或 `UNKNOWN`。只有必要安全條件均確認才是 `READY`；`BLOCKED` 寫明原因及解除條件；`UNKNOWN` 指出缺少的證據及能提供的人。只有 `READY` 才進第二階段。

### 15.3 第二階段：任務辨識與接手

- **目的：**判斷工作是既有任務或新需求，並確認角色、權限、依賴、執行者及准入條件。
- 先盤點 `board/` 與 `board/archive/` 的任務 metadata，再閱讀指定任務及相關任務全文。確認 `from`、`to`、`owner`、`reviewer`、`status`、`depends_on`、`branch`、驗收條件、工作環境及既有成果；不得只看標題或狀態。
- `from` 決定權限歸屬；`to` 是接收對象，`owner` 是主要交付負責人。任何角色不得因被指派、持有分支或能修改檔案，就推定取得另一方的任務狀態權限。
- 確認任務仍有效、依賴已解除、沒有委派鎖定、沒有其他執行者或未保存成果，且任務範圍及驗收條件清楚。若任務已是本方原執行者的 `in_progress`，可以核對後接續，不得虛構重複的 `open` → `in_progress` 轉換。
- **五單容量閘門：**只統計本方 `from` 歸屬且狀態為 `in_progress` 的有效任務；`review`、`open`、`blocked`、`returned`、`done`、`cancelled` 均不計入。唯一資料基準是最新取得的 `origin/main` Board（包含 `board/` 與 `board/archive/`）；不得以本機舊副本、任務分支或未合併內容代替。合計達五張（含五張），不得將其他 `open` 任務轉為 `in_progress`。必須列出占用任務 ID、負責人及來源 SHA。若無法 fetch `origin/main` 或無法完整讀取 Board，結果標示 `UNKNOWN`，不得推定容量未滿，也不得啟動新任務。**開工 PR 合併前必須再檢查一次容量**，避免雙方同時依舊快照開工造成超額。
- **Communicate 優先閘門：**依 §15.9 新定義，使用最新 `origin/main` Board 判斷；觸發時，該 Communicate 工作為本方最高優先級，其他 `open` 任務不得啟動，即使五單容量未滿。若無法取得或完整讀取 Board，Communicate 閘門同樣標示 `UNKNOWN`。人類未明確覆寫並留下紀錄前，不得自行忽略。
- 兩道閘門彼此獨立，必須分別檢查；任一觸發或結果為 `UNKNOWN` 時，其他 `open` 任務保持 `open`。每次 `open` → `in_progress` 前重新檢查。既有任務接手不需重走第三階段，直接進第四階段。
- **結果：**`TAKEOVER`、`WAIT`、`UNAUTHORIZED`、`ALREADY_ACTIVE`、`NEW_REQUEST`、`UNKNOWN`、`CAPACITY_BLOCKED`、`COMMUNICATE_PRIORITY_BLOCKED`。只有合法且兩道閘門均未阻擋的任務可啟動。

### 15.4 第三階段：新需求開單

- **目的：**確認需求不是重複工作，釐清目標、權限、範圍、依賴及驗收方式，建立可追蹤的正式任務。
- 先檢查有效任務與 archive，判斷新需求、既有任務延伸、後續任務或重複需求；確認 `from` 由實際開單方／有權限者決定，不得為方便冒用另一方角色。
- 先完成可自行進行的需求、程式架構及依賴調查。純文件／流程任務不需為開單執行 Supabase SOP；涉及資料庫結構、正式資料、RLS、RPC、trigger、migration 或 Edge Function 才依任務需要取得相應證據。調查不等於獲准修改正式環境。
- 建立新需求紀錄前，再次分別檢查 §15.3 的五單容量及 Communicate 優先兩道閘門。五單已滿、Communicate 閘門觸發或容量結果為 `UNKNOWN` 時，新需求仍可建立並保持 `open`，但不得啟動或開始實作。
- 取得正式任務 ID 後，建立唯一 `task/T-xxxx-short-name` 分支，來源必須是當下最新 `origin/main`；此階段可用只含 `board/` 變更的臨時 Worktree 提交 Board 紀錄，推送後即移除。以該分支建立「開單 PR」，PR head 為任務分支、base 為 `main`，合併使用 merge commit。任務檔或索引推送至任何遠端分支、建立 PR 或合併至 `main`，任一條件先發生即算公開並永久固定 ID。
- 閘門阻擋時仍可提交「開單 PR」，但不得建立正式任務 Worktree 或開始實作。只有通過兩道閘門、任務正式由 `open` 轉為 `in_progress`，且「開工 PR」已合併至 `origin/main` 後，才建立正式任務 Worktree。開工 PR 合併前再檢查一次五單容量及 Communicate 優先閘門。
- 同一任務的「開單 PR」、「開工 PR」、「交付 PR」三階段全部沿用同一任務分支；每次 PR 都以該分支為 head、`main` 為 base，使用 merge commit。每次合併後 fetch，將同一任務分支以 `--ff-only` 同步至最新 `origin/main`，再進入下一階段；不得另建分支承接同一任務。
- `work/<role>` 正常同步完成後必須與 `origin/main` 指向同一 commit、不得領先，且必須能 `--ff-only` 同步；已知過渡分歧依 §7 標示 `KNOWN_DIVERGED`，不視為違規。它們不得作為任務分支來源、PR head 或 Board 任務紀錄整合目的地。分別回讀任務分支與 `origin/main`，確認任務 ID、檔案、索引、branch 欄位、PR head/base、merge commit SHA 及同步結果；未同步的部分不得宣稱完成。
- **結果：**`CREATED`、`CREATED_OPEN_CAPACITY_BLOCKED`、`CREATED_OPEN_COMMUNICATE_PRIORITY_BLOCKED`、`CREATED_OPEN_GATE_UNKNOWN`、`NEED_INPUT`、`DUPLICATE`、`UNAUTHORIZED`、`BLOCKED`、`CANCELLED`。

### 15.5 第四階段：建立／確認 Task Branch 與工作環境

- **目的：**確保一張任務有獨立、可追蹤且不與其他工作混用的工作位置。
- 確認任務 ID、`from`、`to`、`owner`、`branch`、`origin/main` 來源 SHA 及開工 PR 合併 SHA。老查與叉子的任務分支來源一律是 `origin/main`；不得從 `work/<role>` 建立，也不得把 `work/<role>` 當作 upstream 或 PR 來源。
- **Worktree 建立條件：**任務已正式為 `in_progress`，且開工 PR 已合併至 `origin/main`；在此之前不得建立本機 Worktree 或 GitHub App 任務工作環境。條件未滿足時結果為 `BLOCKED`，不得進入實作。
- 一條正式 task branch 只對應一張任務及一個正式工作環境／執行者。檢查是否已有同 ID 分支、其他執行者、未提交／未追蹤／未整合成果及來源不明修改；不得搶做、覆蓋或另開第二個工作環境。
- 回讀並比對任務 ID、branch、Worktree／App 工作位置、來源 SHA、目前 HEAD、PR head/base、merge commit、工作區狀態及 Board `branch` 欄位；PR head 必須是任務分支，base 必須是 `main`。
- **結果：**全部對應且安全為 `READY`；有未保存成果或來源不明為 `BLOCKED`；缺少無法自行取得的證據為 `UNKNOWN`。只有 `READY` 才進第五階段。

### 15.6 第五階段：開發與驗證

- **目的：**依任務範圍完成成果，並用可重複檢查的證據驗證每項驗收條件。
- **進入條件：**第四階段判定 `READY`，且任務狀態必須已是 `in_progress`；實際開始修改前重新檢查五單容量閘門及 Communicate 優先閘門。若任務仍是 `open`、任一閘門阻擋或原任務仍有委派鎖定，不得開始實作。
- 先列出預計修改檔案、用途及預期結果；閱讀現有實作、呼叫端及依賴，確認沒有其他任務正在修改相同內容。不得自行擴大任務範圍。
- 分段實作並保留其他任務及人類留下的修改。遇到覆蓋風險、禁止範圍、來源不明或未授權決策，停止該項寫入，繼續不受影響的唯讀檢查。
- 每項驗收條件都要對應實際修改與證據。文件檢查內容、連結、欄位及規則一致性；程式依變更類型執行建置、測試、靜態檢查或手動操作。
- 分開標示本機、GitHub branch／commit、GitHub Pages、Supabase 正式環境及 Edge Function 的證據；不得用一個環境的結果推定另一個環境已更新。
- 老查修改前後執行 `git diff --check`、`git status --short`，檢查 staged／untracked files，且不得把 `supabase/` 或任何 `.csv` 加入提交。叉子依 GitHub App 可取得的差異及提交預覽檢查，不套用不存在的本機 staged files；雙方都須確認沒有混入其他任務成果。
- 所有適用條件都有證據且差異只含本任務成果，才是 `READY_FOR_INTEGRATION`；失敗可修正時留在本階段重驗；需要人類、權限或外部環境時標示 `BLOCKED`／`UNKNOWN`。

### 15.7 第六階段：內容整合與交付

- **目的：**交付程式碼、文件或其他工作成果；本階段不驗收任務、不更新 `done`。
- **6.1 確認提交內容：**雙方檢查修改內容、未追蹤檔案及提交清單，逐一確認歸屬。老查本機排除 `supabase/` 與所有 `.csv`，不得未檢查就使用 `git add -A`／`git add .`；叉子依 GitHub App 差異及提交預覽檢查。
- **6.2 建立內容提交：**只提交本任務成果；記錄 commit SHA 並回讀檔案清單。提交成功不等於整合或遠端交付。
- **6.3 任務分支保持單一：**不再將任務分支整合回 `work/<role>`；四條 `work/<role>` 必須持續與 `origin/main` 同 SHA。所有任務內容均留在該任務唯一分支，透過交付 PR 合併至 `main`。
- **6.4 遠端內容交付與部署：**同一任務的開單、開工、交付三階段 PR 都以該任務分支為 head、`main` 為 base，並使用 merge commit；每次合併後 fetch，再將任務分支以 `--ff-only` 同步至最新 `origin/main`。Push、建立／合併 PR、部署或操作正式環境，仍須符合 `AGENTS.md` 及本次明確授權；不得將其中一階段的授權擴張到其他階段或部署。
- 內容里程碑分開記錄：`TASK_BRANCH_CREATED`、`OPEN_PR_MERGED`、`WORK_START_PR_MERGED`、`WORKTREE_CREATED`、`DELIVERY_PR_MERGED`、`DEPLOYED`。未執行標示 `NOT_DONE`、`BLOCKED` 或 `UNKNOWN`；這些不是任務驗收狀態。

### 15.8 第七階段：任務驗收與交付

- **目的：**由有權限者確認任務要求達成，並交付正式 Board 任務紀錄；內容交付與任務交付不可混為一談。
- **7.1 確認驗收者：**依 `from` 及權限規則確認。協作者方由 Barry 作最終決定；棒子方由棒子作最終決定。叉子可依授權執行線上檢查，但不得代替棒子作 Owner 專屬決定。
- **7.2 雙路徑驗收：**依任務實際驗收內容選擇本地或線上路徑。若驗收涉及管理員介面或管理員專屬操作，老查本地路徑必須準備 Barry 可實際操作的隔離副本，包含所需操作入口、測試用管理員身分及隔離測試資料；不得冒用棒子的線上管理員身分／憑證或連接正式資料。若任務不涉及管理員介面，則以任務明列的文件檢查、測試、建置或其他可重複驗證方式作為本地驗收，不得為了符合形式而製造無關的管理員介面副本。正式 Supabase 權限或線上專屬設定只能由本地副本明確涵蓋的部分驗證，不得宣稱已驗證正式權限。叉子線上路徑依授權執行；只有棒子有管理員權限的操作，必須由棒子親自執行或確認。任一路徑完整逐項 `PASS` 即可通過，不要求兩路都通過；另一條未執行或受限仍須如實記錄。
- **7.3 處理結果：**至少一條路徑完整 `PASS`，記錄採用路徑、驗收者、逐條結果及證據，並處理非阻斷事項；兩路都未通過，依權限規則退回 `in_progress`；兩路都因外部條件無法驗證，記錄 `blocked`／`UNKNOWN`、等待對象及解除條件。
- **7.4 正式交付及結案：**只有至少一條完整 `PASS` 且 7.3 整理完成，才可由任務所屬方人類決定是否結案，並準備 `done`、`done_by`、`done_at`、`updated`、含「驗收」及非空 `來源：` 的驗收紀錄、archive 及索引變更。Board 任務紀錄的更新仍提交在同一任務分支，透過該任務的交付 PR（head 為任務分支、base 為 `main`、merge commit）交付；不得整合至 `work/<role>`。交付 PR 合併並回讀確認另一方可見後，才完成任務紀錄交付；此為 Board 紀錄交付，不是重新提交或部署遊戲程式。
- **7.5 清理工作環境：**正式結案及任務紀錄交付完成後，才可清理 Worktree／短期分支。先確認成果已整合、提交已保存、沒有未提交／未追蹤／唯一副本資料；不確定就停止清理。

### 15.9 第八階段：跨方工作委派（Communicate Task）

- **定位：**`communicate task` 是正式工作單，不是訊息。`impact` 只通知；需要另一方調查、修改、驗證、提供資料或作出其權限內決定時，必須建立 communicate task。Communicate 優先閘門是跨方工作排程規則，不等同原任務的鎖定紀錄。
- **建立與權限：**由原需求方提出並建立獨立任務；若原需求方無權建立對方權限群組的正式任務，請該權限方建立，絕不可冒用對方的 `from`。`from` 始終是真正開單方，`to` 指派接收方，`owner` 指定執行者。接收方只取得這張委派單明確授予的接單、執行、更新進度、提交成果及回報權，不取得原任務或開單方其他任務的權限。
- **委派資訊：**communicate task 必須有 `## 委派資訊` 區塊，明列 `關聯原任務：T-xxxx`、`原需求方：角色`、`接收方：角色`，且 `reviewer` 指定原需求方。原任務以紀錄標記鎖定及解除，完整格式為 `- YYYY-MM-DD HH:MM [角色] [COMMUNICATE_LOCK] task=T-xxxx actor=角色 at=YYYY-MM-DD HH:MM`；解除時使用 `- YYYY-MM-DD HH:MM [角色] [COMMUNICATE_UNLOCK] task=T-xxxx actor=角色 at=YYYY-MM-DD HH:MM`。`task=` 填 communicate task ID，紀錄必須寫在關聯原任務內；兩處 ID 必須互相對應。不得把一般 `depends_on` 反向當成關聯欄位。
- **鎖定：**委派單成功建立並正式指派後，才在原任務新增鎖定紀錄。鎖定期間，原任務不得被接手／啟動、修改實作內容或再次委派相同工作；不得藉鎖定將原任務標為 `done`，也不改變原任務 `from`、權限歸屬或負責人。委派單建立或指派失敗，不得先鎖原任務。
- **接單及執行：**接收方依授權接手委派單，可將該單 `open` → `in_progress`、`in_progress` ↔ `blocked`，並更新該單進度、branch、成果及證據；不得修改原任務。發現無權執行、需求不清或依賴不成立，將委派單標記 `blocked` 並回報，不得擴大權限。
- **交回：**接收方完成自己負責的部分、提交成果／驗證證據／未完成事項後，將 communicate task 由 `in_progress` 轉為 `returned`。`returned` 只表示接收方已交回，不是 `done`，也不代表原需求完成或已被開單方驗收。
- **接回與補正：**原需求方收到 `returned` 後檢查交付。確認合格時，由原需求方人類記錄接回者、完整日期時間及驗收結果，在原任務新增 `COMMUNICATE_UNLOCK`，解除鎖定，並將委派單標記 `done`；`done_by` 填該人類角色，驗收紀錄須含「驗收」及非空 `來源：`。原任務由原權限方接續。若不合格，記錄差異並將委派單退回 `in_progress` 補正，鎖定持續。只有原需求方確認接回才可解鎖。若 `from` 不屬原需求方，原需求方僅取得這張委派單的 `returned` → `done`／`in_progress` 接回確認權，不取得其他狀態操作權；`done` 仍須由原需求方人類決定。
- **取消、阻塞及逾期：**取消或無法執行時由原需求方確認處置；解除鎖定前確認原任務可安全恢復、接收方沒有未保存成果及是否需要改派。不得因逾期、已讀或暫時無回覆自動解鎖。
- **優先閘門觸發條件：**雙方各自獨立判斷本方角色群組。只要存在有效 communicate task，符合以下任一條件即觸發本方閘門：① `to` 指派給本方，且狀態為 `open` 或 `in_progress`；② `from` 歸屬本方，且狀態為 `returned`。不得只檢查 `from` 或只檢查 `in_progress`。
- **閘門效果：**觸發後，該 Communicate 工作為本方最高優先級；本方其他 `open` 任務不得轉為 `in_progress`，也不得開始實作，即使五單容量未滿。新需求可以建立並保持 `open`。既有任務的權限、鎖定及狀態不因閘門自動改變；閘門不會把一般任務變成 communicate task。
- **人類覆寫：**只有本方有權限的人類可明確覆寫；必須在準備啟動的任務紀錄中寫明觸發的 communicate task ID、決策者、覆寫原因、允許範圍及有效期限／解除條件。沒有這筆紀錄即視為未覆寫；GPT 不得自行解除或忽略閘門。
- **與容量閘門的關係：**Communicate 閘門與五單容量閘門彼此獨立，必須分別檢查；`returned` 會觸發 Communicate 閘門，但不計入五單容量，也不等於原任務已完成。只有條件不再符合或人類完成有效覆寫，才可重新評估其他 `open` 任務。
- **結果：**`NOT_REQUIRED`、`NOTICE_ONLY`、`TASK_CREATED`、`LOCKED`、`IN_PROGRESS`、`returned`、`REWORK`、`BLOCKED`、`CLOSED`。只有原需求方確認接回並解除鎖定，委派流程才是 `CLOSED`；原任務仍依自己的驗收條件決定是否完成。
