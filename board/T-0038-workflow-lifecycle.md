## 新版流程架構

### 第一階段：工作環境准入

目的：確認目前使用的環境、角色、分支及工作區正確、安全，而且具備開始工作的條件。

1.1 確認 AI 身分與代表角色：老查代表 barry／`collaborator_side`；叉子代表棒子／`owner_side`。雙方均須確認自己是誰、代表誰、能執行哪些操作；不得冒充另一方。

1.2 確認 Repository 與外掛環境：老查只檢查本機 Repository，以及 GitHub 線上 Repository 的狀態與提交關係；不在本階段執行 Supabase SOP，也不讀取或索取 Supabase 憑證。叉子檢查 GitHub 外掛與 Supabase 外掛是否正常、GitHub 線上 Repository 狀態，以及 Supabase 專案狀態。老查的 Supabase SOP 延後至任務正式開單後，再依任務內容判斷是否需要執行；純規格、流程或一般文件任務不需要 Supabase 即時狀態，涉及資料庫結構、正式資料、RLS、RPC、trigger、migration 或 Edge Function 的任務才需要相應證據。不得因為某角色有憑證或外掛，就推定另一角色也有。

1.3 確認目前分支與角色分支：雙方都要確認目前實際工作基準、commit SHA、角色整合分支及任務工作環境。老查檢查本機 branch、HEAD、upstream 與目錄綁定；叉子檢查 GitHub App 實際使用的線上 branch／PR base／commit SHA 及 App 工作環境，不要求叉子提供不存在的 Barry 本機路徑或 upstream 設定。不能只看分支名稱。

1.4 確認 Git 同步與提交關係（雙方共用判斷標準、依環境採不同操作）：目的在確認角色整合分支、共同 `main` 及目前任務分支的實際提交基準。不得只看 branch 名稱或 ahead／behind 數字就拒絕整個任務；必須取得可核對的 commit SHA，查明差異來源、任務歸屬及對目前工作的影響。老查與叉子都必須分開比較「自己的 `work/<role>` 對共同 `main`」及「目前 task branch 對自己的 `work/<role>`」，不得把它們混成同一個同步目標。

   **老查（有 Barry 本機 Repository）：**
   - 執行 `git fetch origin` 更新遠端追蹤資訊；fetch 不會自行修改本機分支。
   - 比較本機 `work/laocha` 與 `origin/work/laocha`，記錄兩邊 HEAD、ahead／behind、merge-base、各自獨有提交及提交內容。這是本機角色分支與線上角色分支的同步檢查。
   - 另外比較本機 `work/laocha` 與 `origin/main`，確認 main 是否有尚未納入角色分支的提交，以及角色分支是否有 main 沒有的提交。`origin/main` 是整合狀態比較對象，不是角色分支同步目標，也不是 `work/laocha` 的 upstream。
   - 比較目前 task branch 與 `work/laocha`，確認任務分支建立時的基準、雙方獨有提交及差異是否影響目前工作。任務分支落後角色分支不等於錯誤，不要求每次准入都自動同步。
   - 只有本機單純落後、遠端是本機祖先、工作區乾淨、沒有其他 Worktree 或任務安全疑慮時，才可將本機角色分支 fast-forward 到線上角色分支。若本機領先，先確認領先提交的來源及任務歸屬並保留，不得自動 push。若分歧，先分析雙方獨有提交，再評估 merge、選擇性 cherry-pick、保留現況或請 Barry 決策。

   **叉子（沒有 Barry 本機 Repository）：**
   - 以 GitHub 線上 Repository 為權威來源，使用 GitHub 外掛可讀取的 branch、commit、compare／PR 等資訊，確認 `work/chazi` 與 `main` 的 HEAD SHA、共同祖先、雙方獨有提交及提交內容；不可要求叉子執行 Barry 電腦上的 `git fetch`、讀取 Barry 本機路徑或列出 Barry 的 Worktree。
   - 另外確認目前 GitHub App 工作環境實際使用的 branch 與 HEAD SHA，並比較該工作基準與線上 `work/chazi`。若 App 有自己的臨時 clone／工作目錄，可檢查該環境自身的狀態，但必須明確標示為 App 工作環境，不得稱為 Barry 的本機 Worktree。
   - 若 `work/chazi` 落後 `main`，先檢查角色分支是否另有獨有提交，再評估透過 GitHub 支援的整合方式納入 main；若角色分支領先，先確認領先提交是否為合法工作並保留；若雙方分歧，逐一檢查各自獨有提交及任務歸屬，再評估 PR、合併或選擇性整合。GitHub 權限不足或 compare 資料不完整時，記錄缺少的證據，不可假裝已驗證。
   - 不得把 GitHub 線上 Repository 的狀態與 App 暫存工作環境混為一談；也不得因為叉子沒有本機環境，就省略提交關係檢查。

   **雙方共用的提交關係分類及處置：**
   - `SYNCED`：比較對象指向相同提交，記錄 SHA 後繼續。
   - `BEHIND`：本方落後對方。先確認本方是否有獨有提交；若確定只是單純落後，且工作區、權限及任務歸屬安全，再使用該環境支援的 fast-forward／GitHub 整合方式。若仍有獨有提交，不得當成單純落後處理。
   - `AHEAD`：本方有對方沒有的提交。檢查提交來源、任務歸屬及是否已交付；合法成果先保留，不得為了表面同步而自動 push 或丟棄。
   - `DIVERGED`：雙方各有獨有提交。先列出各自提交及檔案差異，確認任務歸屬、衝突及整合權限，再選擇保留、merge、選擇性 cherry-pick、PR 或請有權限的人類決策；不得直接選 ours／theirs。
   - `UNKNOWN`：無法取得 SHA、compare、提交內容或必要權限。指出缺少哪項證據及由誰提供；只阻擋依賴該證據的寫入或整合，不阻擋不受影響的唯讀盤點。

   **同步及阻擋原則：**
   - ahead／behind、不同 commit ID 或存在分歧本身不是拒絕整個任務的理由。應依影響範圍決定可否讀取、盤點、建立工作區或修改程式；若基準不明、可能混入他人未整合成果、存在未解衝突或無法確認寫入安全，才阻擋受影響的操作。
   - 技術上可合併不代表政策上已獲授權。同步或整合前必須確認方向、提交歸屬、工作區安全及權限；不得丟棄提交、改寫歷史、強制 push 或以同步為由覆蓋他人工作。
   - 老查若要將本機提交 push 至線上，仍須本次明確授權；叉子使用 GitHub 線上操作時，也必須遵守 Repository 權限、分支保護及本流程授權。不得將准入檢查視為自動授權一般程式碼 push。
   - 任務分支 upstream／來源關係：老查實際檢查本機 `task/T-xxxx-*` upstream 必須指向本人本機 `work/laocha`，不得指向 `main`、遠端角色分支或其他任務分支。叉子若使用 GitHub 線上工作流，則檢查 task branch 的建立來源、PR base／compare 方向及實際 commit 關係，確認它以本人 `work/chazi` 為角色整合基準；不得要求沒有本機 Git 設定的叉子虛構本機 upstream。雙方均須確認 task branch 與角色分支的提交差異及任務歸屬。
   - 任何同步或整合完成後，依各自環境重新取得 branch、HEAD SHA、提交關係、工作區及任務歸屬證據，記錄前後結果；仍有差異必須說明，不可宣稱完全同步。

1.5 確認 Worktree 與工作區安全（雙方共用安全目標、依環境採不同檢查）：目的在確認目前工作位置不會與其他任務混用，且不會覆蓋他人或其他任務成果。**老查本機 SOP：**列出 `git worktree list --porcelain`、`git branch -vv`，確認目前路徑、branch、HEAD、upstream、`git status --short --branch`、未提交修改、staged files、未追蹤檔案、未整合 commit 及用途不明項目；逐一核對每條 branch 只能綁定一個 Worktree，task branch upstream 指向本人本機 `work/laocha`。**叉子 GitHub SOP：**不要求列出 Barry 本機 Worktree；改以 GitHub 線上 branch、commit SHA、PR、Board 任務紀錄及 GitHub App 自己的工作環境為證據，確認目前工作分支、任務 ID、建立來源、是否已有相同任務的執行分支／PR，以及 App 工作目錄可取得的未提交修改或未保存成果。若 App 工作環境無法提供未提交狀態，必須明確記錄這項限制；在確認工作基準及成果保存位置前，不得進行可能覆蓋資料的寫入。

   **雙方共用規則：**一條正式 task branch 只能對應一個正式任務及一個執行工作環境；對老查而言是 branch 與本機 Worktree 一對一，對叉子而言是 branch 與 GitHub App 任務工作環境／執行工作階段一對一，不得讓兩個獨立工作者同時修改同一任務分支。每個工作環境都要能指出用途、任務 ID、branch、基準 SHA、成果保存位置及執行者。若發現重複使用、分支與用途不符、已有其他執行者、未提交修改、未追蹤檔案或未整合成果，先停止受影響的寫入，分類並保留資料，再提出安全處置；不得自行覆蓋、刪除或拆除仍有資料的工作區，也不得因久未活動就刪除。叉子若無法確認 App 工作環境是否仍有未保存成果，必須先確認或建立安全保存方式，不能把「GitHub branch 看起來乾淨」當成 App 工作區也乾淨。

1.6 最終准入判定：`READY` 表示必要條件均已確認且可安全開始；`BLOCKED` 表示有已知阻礙，必須說明原因、影響、已做處置及解除條件；`UNKNOWN` 表示缺少無法自行取得的資訊，必須明確指出只有哪位人類／具權限者能提供什麼資料，以及取得後如何驗證。若未知資訊與本次任務無關，應記錄限制，不得把非必要檢查變成永久關卡；若影響安全或正確性，才阻擋相關工作。

### 第二階段：任務辨識與接手

目的：在已通過第一階段的安全環境中，找出目前要處理的工作，判斷它是既有任務還是新需求，並確認自己是否有權限及條件接手。

進入條件：第一階段結果必須是 `READY`。若不是 READY，不得讀取完整任務內容或進行接手；應先處理第一階段列出的問題。

2.1 Board 任務索引盤點：先讀取 Board 使用規範及任務索引，只盤點必要 metadata，例如任務 ID、標題、狀態、`from`、`to`、`owner`、`depends_on`、`branch`。同時查看有效任務區與 archive 的索引，避免漏掉已封存、已完成或曾經處理過的相似任務。此步驟不必先打開每一份任務全文。Board 在老查與叉子的角色 Worktree 中都採「全部任務可見」；可見不代表有權修改，操作權仍由任務歸屬及 Board 規範決定。

2.2 任務內容辨識：依照使用者指定的任務 ID、目標或索引篩選結果，閱讀相關任務完整內容及必要的關聯紀錄。確認任務目標、工作範圍、禁止事項、驗收條件、目前進度、最後更新及是否已有交付證據。不得只看標題或狀態就認定可以接手。

2.3 任務權限確認：逐一確認 `from`、`to`、`owner`、`reviewer`。`from` 是任務權限歸屬的主要依據；`to` 是預定接收對象，`owner` 是目前負責執行者，`reviewer` 是驗收／審查角色。老查不得接手、修改狀態或代替棒子驗收 `from: 叉子` 的任務；叉子亦不得接手、修改狀態或代替 Barry 驗收 `from: 老查` 的任務。若任務欄位互相矛盾或權限歸屬不明，先列為待確認，不得自行改寫權限欄位。

2.4 任務狀態、依賴與雙重啟動閘門：確認 `status` 是否仍可執行，`depends_on` 是否全部解除，依賴任務是否已達到所需狀態，並檢查是否被有效的 `communicate task` 鎖定。**本節有兩道不同且必須同時遵守的限制，不得互相取代：**

   - **五單容量閘門（保留原規則）：**統計我方所有 `from` 歸屬本方且狀態為 `in_progress` 或 `review` 的有效任務。數量達到五張（含五張）時，不得將任何其他 `open` 任務轉為 `in_progress`。未達五張時，仍可依其他規則判斷是否啟動；`review` 必須計入容量，不能因不在執行中就漏算。
   - **Communicate 優先閘門（新增規則）：**我方只要存在一張有效、`from` 歸屬本方且 `status: in_progress` 的 `communicate task`，該委派工作就自動成為我方最高優先級；在它完成或依規則正式交接前，不得將我方其他任何 `open` 任務轉為 `in_progress`，即使五單容量尚未用滿也一樣。此限制只由進行中的 `communicate task` 觸發，不得擴大解釋成任何一般 `in_progress` 任務都會觸發單一任務限制。

   兩道閘門都必須在接手、啟動或建立會開始實作的工作環境前檢查，且每次 `open → in_progress` 前重新確認。新需求可建立並保持 `open`，但不得藉由建立新任務或工作環境繞過任一閘門。若目前沒有進行中的 `communicate task`，且五單容量未滿，才可依任務優先級、依賴、緊急程度及可執行性選擇下一張任務啟動。`done`、`archived`、`cancelled` 等已結束任務不得直接當成待接手工作；若要重新處理，應先確認是原任務重開、建立後續任務，還是新需求，不得自行改狀態。`blocked` 或依賴未完成時，記錄阻礙及解除條件。

2.5 工作區與執行者確認：檢查任務是否已有 `branch`、對應工作環境、未提交修改、未追蹤檔案、未整合 commit，或其他 AI／人類正在執行。老查核對 branch／本機 Worktree 一對一及 task branch upstream 指向本人本機 `work/laocha`；叉子核對 GitHub 任務分支、PR base／來源及 App 工作環境，不要求本機 Worktree 或 upstream 設定。若已有人處理，不得另開第二個工作區搶做；應確認是否由原執行者繼續、正式交接，或等待其完成。若任務成果已整合，應先判斷剩餘工作，不可重複實作已完成部分。

2.6 接手判定與分流：只有在任務仍有效、權限正確、依賴已解除且未被鎖定、工作範圍與驗收條件清楚，而且沒有未處理的執行者／工作區衝突時，才能判定可接手。接手前必須同時檢查 2.4 的五單容量閘門及 Communicate 優先閘門：若我方有進行中的 `communicate task`，它優先於其他所有 `open` 任務；若我方 `in_progress` 與 `review` 有效任務合計已達五張，也不得啟動其他 `open` 任務。兩道閘門任一觸發，其他 `open` 任務均保持 `open`。只有兩道閘門都未觸發，才可依任務優先級等條件選擇一張任務啟動。依 Board 規範留下接手紀錄，更新允許變更的負責人及工作區欄位；不得改動 `from` 來轉移權限。接手既有且已是 `in_progress` 的任務，若本方就是原執行者，可繼續原工作；不得藉此接手別人的工作或新增第二張進行中任務。接手完成後進入第四階段，不需重走第三階段。若確認沒有可接續的既有任務，或使用者明確提出新需求，才分流到第三階段；新需求可先建立為 `open`，但不得繞過任一閘門。

第二階段判定結果：
- `TAKEOVER`：權限、依賴、範圍及工作區條件均符合，可正式接手既有任務，下一步進第四階段。
- `WAIT`：任務存在，但依賴或其他阻礙尚未解除；記錄阻礙及解除條件。
- `UNAUTHORIZED`：任務屬於另一方或目前角色沒有相應權限；不得接手或修改。
- `ALREADY_ACTIVE`：已有執行者或工作區正在處理；不得重複開工，先確認交接方式。
- `NEW_REQUEST`：沒有可接續的既有任務，或使用者明確要求建立新任務；下一步進第三階段。
- `UNKNOWN`：關鍵欄位或執行狀態無法確認；完成其他安全檢查後，一次列出需要人類補充的資訊。
- `CAPACITY_BLOCKED`：我方 `in_progress` 與 `review` 有效任務合計已達五張；五單容量閘門阻止其他 `open` 任務啟動。
- `COMMUNICATE_PRIORITY_BLOCKED`：我方已有一張有效且 `in_progress` 的 `communicate task`；該委派工作自動列為最高優先級，其他 `open` 任務不得啟動。

### 第三階段：新需求開單

- 進入條件：第二階段判定為 `NEW_REQUEST`，或使用者明確提出新需求；第一階段仍須為 `READY`。
- **3.1 確認需求是否真的新**：檢查有效 Board 任務及 archive 的索引與相關任務內容，判斷是全新需求、既有任務延伸、已完成任務追加、重複需求或應重開的原任務。已完成任務的新增功能原則上建立後續任務，保留舊任務歷史；只有原驗收遺漏或實際未完成才評估重開。
- **3.2 確認開單方與權限**：確認提出需求的人、`from` 權限歸屬、`to` 接收對象、`owner` 執行者及 `reviewer` 驗收者。`from` 由需求提出方／有權限者確認，不得由實際執行 AI 為了方便自行改寫；欄位矛盾時先列待確認。
- **3.3 把需求說清楚**：確認目標、預期成果、範圍、禁止事項、依賴、驗收條件及風險。AI 能從 Repository、Board 或可靠資料自行查明的內容應先查，不要把可自行調查的工作推給人類；仍不完整的部分可以先記錄為待補，但必須標示哪些工作不能開始。
- **3.4 確認技術根基與必要依賴**：確認前置任務、現有架構及必要技術條件。純規格、流程或一般文件任務不需要為了開單而執行 Supabase SOP；涉及資料庫結構、正式資料、RLS、RPC、trigger、migration、Edge Function 等，才依任務需要取得相應證據。技術根基未確認時，阻擋依賴該技術事實的實作，不代表不能建立 `open` 任務或先做不受影響的調查。技術調查不等於授權修改正式環境。
- **3.5 雙重啟動閘門（硬性限制）**：建立新需求紀錄前，再次分別檢查兩道閘門，兩者不得互相取代：
  - **五單容量閘門（原規則持續有效）：**統計我方 `from` 歸屬本方且狀態為 `in_progress` 或 `review` 的有效任務；達五張（含五張）時，不得將其他 `open` 任務轉為 `in_progress`。必須列出占用容量的任務 ID、狀態及負責人，並建議優先接續／完成哪一張及理由；不得只回報「已滿五張」。
  - **Communicate 優先閘門（新增規則）：**我方只要存在一張有效、`from` 歸屬本方且 `status: in_progress` 的 `communicate task`，該委派工作自動列為最高優先級；其他 `open` 任務不得啟動，即使五單容量尚未滿額。

  新需求仍可建立並保持 `open`，但不得啟動、不得建立會開始實作的工作分支，也不得以人類要求、任務很小或 AI 自認有空為由例外。必須等觸發的閘門解除後，再重新檢查是否可啟動下一張。不得透過虛假改狀態、修改 `from` 或先建立工作環境規避。技術根基閘門、五單容量閘門及 Communicate 優先閘門是不同原因，必須分開回報。
- **3.6 建立正式 Board 任務紀錄並取得 ID**：依 Board 規範檢查有效任務區與 archive 的最大 ID、防止撞號，建立正式任務檔及索引。資訊尚未完整時，可先寫入已確認內容，將缺漏明確標示為待補，並保持 `status: open`；不得因任務檔已建立就視為已獲准開工。新任務建立成功後取得正式 ID，後續分支名稱必須使用該 ID。
- **3.7 建立 Task Branch 與獨立工作環境**：取得正式 ID 後，才建立 `task/T-xxxx-short-name`。老查從已確認安全的本機 `work/laocha` 建立一個獨立 Worktree，並實際驗證一條 branch 只綁定一個 Worktree、task branch upstream 指向本機 `work/laocha`。叉子從已確認安全的線上 `work/chazi` 建立任務分支，使用 GitHub App 支援的獨立任務工作環境；不要求叉子建立 Barry 本機 Worktree，但必須確保一條任務分支只由一個正式工作環境／執行者使用。雙方都要檢查同 ID 分支是否已存在、來源 SHA、工作區狀態及是否混入其他任務成果。若建立工作環境時遇到提交領先／落後／分歧，依 1.4 的影響範圍規則處理，不得自動丟棄或改寫歷史。建立分支及工作環境只代表隔離位置已備妥，不等於已獲准進入開發；若五單容量閘門或 Communicate 優先閘門阻擋啟動，任務保持 `open`，不得開始程式碼修改。
- **3.8 同步任務紀錄並驗證跨 AI 可見性**：任務檔、Board 索引及必要的分支 metadata 必須讓其他 AI 在共同 Repository 中看得到，不能只留在個人 task branch。新開單流程已獲限定預先授權：可以將**本次 Board 任務紀錄、索引及必要的任務分支資訊**同步到開單方自己的 `work/<role>`，並再同步到共同 `main`；此授權不包含遊戲程式、Supabase、部署或其他任務成果。先將 Board 任務紀錄及索引提交在本次 task branch，再只把這些 Board 紀錄變更整合到角色 `work` 及共同 `main`；不得把其他尚未完成的 task branch 程式碼一併帶入。角色 `work` 只整合本次 Board 紀錄提交；共同 `main` 只透過 PR 或選擇性 cherry-pick 等既定方式整合同一份 Board 紀錄，不得為了同步新任務而把整個角色分支或其他任務程式碼帶入。同步時須遵守分支保護及既定整合方式；若提交歷史分歧，先比較並只選擇本次 Board 紀錄，不得整條分支盲目合併。完成後分別讀取角色 `work`、`main` 及任務分支，核對任務 ID、檔案、索引、branch 欄位及 commit SHA，確認其他 AI 可透過共同 Repository 看見任務。任何一邊未同步或驗證失敗，都不得宣稱開單流程完成；記錄實際完成部分及缺少的權限／證據。

第三階段判定結果：
- `CREATED`：正式 Board 任務、Task Branch／工作環境及 `work`、`main` 的任務紀錄同步均完成，且已回讀驗證。
- `CREATED_OPEN_CAPACITY_BLOCKED`：任務紀錄已建立並保持 `open`，但我方 `in_progress` 與 `review` 有效任務合計已達五張，禁止啟動新任務。
- `CREATED_OPEN_COMMUNICATE_PRIORITY_BLOCKED`：任務紀錄已建立並保持 `open`，但我方有進行中的 `communicate task`，因此禁止啟動其他任務。
- `NEED_INPUT`：需求或權限仍有必要資訊待人類補充；已完成所有安全可行調查並集中列出問題。
- `DUPLICATE`：需求已由既有任務涵蓋，不另開重複任務。
- `UNAUTHORIZED`：提出者或執行角色沒有建立／修改該任務的權限。
- `BLOCKED`：技術根基、依賴、分支安全或跨分支同步存在明確阻礙；列出受影響操作及解除條件。
- `CANCELLED`：需求提出方決定不再建立。

### 第四階段：建立／確認 Task Branch + 工作環境

進入條件：既有任務已完成第二階段接手，或新任務已完成第三階段 3.7／3.8。新需求在第三階段已建立工作環境者，本階段不得重複建立；既有任務尚無工作環境者，才在本階段建立。

- **目的：**讓一張任務有專屬且可辨識的工作位置，避免不同任務共用同一個分支或互相覆蓋成果。
- **子階段 4.1：確認任務與分支名稱。**確認任務 ID、`from`、`owner`、`branch` 及第四階段進入條件；正式任務 ID 取得後才能建立 `task/T-xxxx-short-name`。若 Board 的 `branch` 與實際分支不一致，先查明並記錄，不自行改寫任務歸屬。
- **子階段 4.2：確認建立來源。**從本人已確認安全的角色整合分支建立獨立工作環境；老查建立本機 Worktree，叉子使用 GitHub App 支援的獨立任務工作環境。記錄來源分支及 HEAD SHA，並依第一階段 1.4 檢查提交關係。若角色分支與 `main` 或 task branch 有差異，依提交來源及任務影響判斷，不可只因 ahead／behind 就拒絕，也不可跳過提交歸屬檢查。
- **子階段 4.3：確認唯一工作環境。**檢查是否已有同 ID 分支／工作環境、其他執行者、未提交修改、未追蹤檔案或未整合成果。一條正式任務分支只能對應一個正式任務及一個執行工作環境；老查驗證 branch／Worktree 一對一，叉子驗證 branch／GitHub App 任務工作環境一對一。標準任務分支與工作環境依 Board 規範預先授權；非標準分支、跨角色分支或實驗性工作環境需另行確認。
- **子階段 4.4：回讀驗證。**新需求回讀第三階段建立的目錄／branch／HEAD／status／Worktree 或 App 工作環境資料，並確認 3.8 同步結果。既有任務則驗證建立後的目前目錄、branch、HEAD、status 及 Worktree／App 工作環境清單。兩種路徑都要確認任務 ID、分支、工作位置及 Board `branch` 欄位互相對應。
- **判斷與處置：**全部對應且工作區可安全使用，判定 `READY`；已有其他執行者、未保存成果或分支來源不明，判定 `BLOCKED`，保留現況並列出解除條件；缺少 GitHub App 工作環境證據等無法自行取得的資訊，判定 `UNKNOWN`，指出需要哪位人類或哪個工具提供資料。不得自行刪除、覆蓋或另開第二個工作環境搶做。
- **退出條件與交付：**只有 `READY` 才能進第五階段。交付任務分支名稱、工作環境位置／識別、來源分支與 SHA、目前 HEAD、upstream 或線上 PR base、工作區狀態及一對一檢查結果；`BLOCKED`／`UNKNOWN` 則交付缺漏、影響及解除方式。

### 第五階段：開發與驗證

- **目的：**依任務的範圍完成成果，並用可重複檢查的證據確認成果符合驗收條件。
- **進入條件：**第四階段判定 `READY`；任務仍由目前角色負責，工作目錄、分支及基準 SHA 已確認，且任務範圍、禁止事項及驗收條件可供執行。若工作中發現任務已被其他人接手或基準改變，先重新檢查受影響部分。
- **子階段 5.1：建立修改清單。**逐項對照任務範圍，列出預計修改的檔案、用途及預期結果。讀取檔案與呼叫端，確認現有做法、依賴及是否有其他任務正在修改；新增檔案也要確認所屬功能及放置位置。發現超出任務範圍的必要修改時，先記錄原因及影響，不能自行擴大授權。
- **子階段 5.2：分段實作。**依任務範圍逐項修改，每次修改前確認檔案來源、用途及工作區狀態；保留其他任務及人類留下的未提交成果。若發現資料可能被覆蓋、提交來源不明、需要修改禁止範圍，或必須作出未授權的產品／正式環境決策，停止該項寫入，繼續其他不受影響的唯讀檢查。
- **子階段 5.3：對照驗收條件。**把每項驗收條件對應到實際修改及可檢查證據。文件任務檢查內容完整性、連結、欄位及前後規則一致性；程式任務依變更類型選擇建置、單元／整合測試、靜態檢查或手動操作。不得只因程式能編譯或文件能開啟，就推定所有功能條件都通過。
- **子階段 5.4：分開驗證各環境。**本機測試只證明本機結果；GitHub branch／commit 證明遠端程式碼狀態；GitHub Pages 證明線上頁面部署版本；Supabase 查詢證明指定專案當下資料庫狀態；Edge Function 部署資訊證明指定函式版本。只有任務確實涉及該環境且具備授權時才執行相應驗證，並記錄專案／環境、時間、版本或查詢依據。不得把一種環境的證據當成另一種環境已完成。
- **子階段 5.5：檢查修改品質與工作區。**執行適合本次變更的測試，記錄完整命令及 exit code；修改前後執行 `git diff --check`、`git status --short`，並檢查 staged files、未追蹤檔案及差異內容。老查須確認沒有把 `.csv` 或 `supabase/` 內容加入本機提交；叉子則依 GitHub App 可取得的差異及提交預覽檢查，不套用老查的本機檔案限制。雙方都要確認沒有混入其他任務成果。測試不適用或無法執行時，寫明原因及尚未驗證的範圍。
- **判斷與處置：**所有適用驗收條件均有通過證據、差異只包含本任務成果且工作區狀態清楚，才可判定 `READY_FOR_INTEGRATION`；有可修正失敗就留在本階段修正並重跑受影響驗證；需要人類決策、權限或外部環境證據時，標記 `BLOCKED`／`UNKNOWN`，列出影響與解除條件。若某一測試失敗，不得將其餘成功測試合併描述成整體通過。
- **退出條件與交付：**交付修改檔案清單、主要差異、逐項驗收條件結果、測試命令及 exit code、環境證據、未驗證項目、風險、影響任務及目前 Git 狀態。只有 `READY_FOR_INTEGRATION` 才進第六階段；其餘狀態保留在第五階段並集中提出待處理事項。

### 第六階段：內容整合與交付

- **目的：**只把第五階段完成的程式碼、文件或其他工作成果交付到指定位置；本階段不驗收任務、不更新 `done`，也不代表委託已完成。

### 第八階段：跨方工作委派（Communicate Task）

- **目的：**把「通知對方」與「請對方實際做事」分開。`impact` 僅負責通知受影響的人，不再充當待辦清單或工作指令；需要另一方執行工作時，必須建立正式 `communicate task`，指派給具有該項權限的一方。
- **定位：**`communicate task` 是正式工作單，不只是訊息。開單方保留原需求及最終確認權；接收方只取得這張委派單明確授予的接單、執行、更新進度、提交成果及回報權，不因此取得原任務或開單方其他任務的權限。此機制可在第一至第七階段按需啟動。
- **子階段 8.1：判斷是否需要委派。**若只是讓對方知道某件事，使用 `impact` 通知即可；若需要對方調查、修改、驗證、提供資料、作出其權限內決定或完成其他具體工作，就必須建立 `communicate task`。不得只在 `impact` 寫「請某人處理」並期待對方自動承擔工作。
- **子階段 8.2：建立正式 communicate task。**由原需求／依賴任務的開單方建立獨立任務，填明 `from`、`to`、`owner`、`reviewer`、工作目標、範圍、禁止事項、交付物、驗收條件、期限、證據及被委派的權限。接收方必須是對該工作具有實際權限的一方；若開單方無權建立對方權限群組的正式任務，須請該權限方建立，不能冒用其 `from`。委派單必須用明確的關聯欄位或紀錄連結原本等待這項工作的任務（下稱 `depend task`），不得把一般 `depends_on` 依賴關係反向使用，以免錯誤阻止委派單接手。
- **子階段 8.3：鎖定 depend task。**`communicate task` 建立並正式指派後，必須把關聯的 `depend task` 標記為跨方委派鎖定，並在原任務紀錄中留下鎖定狀態、對應 `communicate task` ID、鎖定者及時間，讓雙方都能查到。鎖定期間，原任務不得被接手、啟動、修改實作內容或另行委派相同工作，避免雙方同時處理同一件事。鎖定不等於把原任務標記為 `done`，也不改變原任務的 `from`、權限歸屬或負責人。若委派單建立失敗或未正式指派成功，不得先鎖定原任務。
- **子階段 8.4：接收方接單及執行。**接收方確認任務權限、工作範圍及依賴後，依一般任務流程接手並執行；接收方可更新這張 `communicate task` 的進度、分支、成果及證據，但不得修改原 `depend task`。接收方若發現無權執行、需求不清或依賴不成立，應將委派單標記為適當的阻塞狀態並回報開單方，不得自行擴大權限。
- **子階段 8.5：接收方完成並交回。**接收方確認自己被指派的工作已完成，提交成果、驗證證據及未完成事項後，將 `communicate task` 轉為新增狀態 **`returned`**。`returned` 的意思是「接收方負責的部分已完成，正式交回開單方接續處理」；它不是 `done`，不代表原需求已完成，也不代表開單方已驗收。接收方不得自行把原 `depend task` 標記完成。Barry 已於 2026-11-07 明確授權將 `returned` 正式納入 `board/README.md`、`_TEMPLATE.md` 及 Board 驗證工具；本任務已將其正式落實，無須再將其列為待授權事項。
- **子階段 8.6：開單方接回及解除鎖定。**開單方收到 `returned` 後，檢查交付物及證據。確認接收方的委派工作已完成後，在原任務及委派單留下接回者、時間、驗證結果，並解除 `depend task` 的委派鎖定；原任務回到開單方可處理狀態，由開單方依原任務流程繼續工作、整合或驗收。若交付不完整或不符合要求，鎖定不得解除；開單方應在 `communicate task` 留下具體差異並退回接收方補正。只有開單方確認接回，才可解除鎖定。
- **子階段 8.7：處理取消、阻塞及逾期。**若委派工作取消或無法執行，必須由開單方確認如何處理；解除鎖定前，先確認原任務是否可安全恢復、委派方是否仍有未保存成果及是否需要改派。不得因為逾期、已讀或接收方暫時無回覆就自動解鎖。所有阻塞均記錄等待對象、原因、影響及下一步。
- **子階段 8.8：impact 純通知及溝通紀錄。**`impact` 只記錄事件、受影響對象、影響範圍及通知連結，例如「已建立 T-xxxx communicate task，請至該任務查看」；不得在 `impact` 本身派工作、要求執行、追蹤待辦或重複提醒誰應做什麼。工作指派、進度及交付只以 `communicate task` 為準。通知送達或已讀不等於接單、同意、授權或驗收。
- **判斷與處置：**`NOT_REQUIRED` 表示不需跨方處理；`NOTICE_ONLY` 表示只需透過 `impact` 通知；`TASK_CREATED` 表示正式委派單已建立；`LOCKED` 表示 depend task 已鎖定；`IN_PROGRESS` 表示接收方執行中；`returned` 表示接收方已完成其部分並交回開單方；`REWORK` 表示開單方要求補正；`BLOCKED` 表示委派工作受阻；`CLOSED` 表示開單方已接回、確認交付並解除鎖定。`returned` 不得與 `done` 混用。
- **退出條件與交付：**提供 communicate task ID、開單方與接收方、權限依據、關聯 depend task ID、鎖定證據、交付物及驗收證據、`returned` 時間、開單方接回確認及解除鎖定紀錄。只有開單方完成接回確認並解除鎖定，這次委派流程才算 `CLOSED`；原任務仍依自己的驗收條件決定是否完成。

## 全流程共通規則：集中彙整後才暫停

1. 每個階段先跑完所有安全可行的子階段檢查，不因第一個缺漏就立即詢問。
2. 每項缺漏先記錄：所在子階段、已知事實、未知內容、影響及是否有安全替代方案。
3. 繼續其他不受影響的唯讀檢查；若後續操作可能覆蓋資料、破壞歷史或造成不可逆影響，立即停止該項操作。
4. 該階段所有可執行子階段完成後，一次列出全部缺漏、異常及待決策事項，再暫停。
5. 本節規則由老查與叉子雙方共同遵守，不得只要求其中一方採用。需要人類決策時，每一個決策各自整理成 A／B／C／D／E 選擇題，E 固定為「其他做法（請自行描述）」。有可靠建議時，建議方案必須放在 A，並標示實際提出建議的一方（例如「老查建議」或「叉子建議」），說明理由；其他方案說明結果與代價。沒有可靠建議時，不得硬推某方案，必須中立列出各方案的優點、缺點及適用情況。
6. 所有決策題目使用國中生能理解的白話；不得預設使用者懂 Git 或其他技術知識。必要術語要在同一句或緊接著用生活化例子解釋，並說明它對這次決定的實際影響。每題只問一個決定，交代現況、為何需要決定、選擇後的結果及驗證方式。
7. 人類補充資訊後，回到受影響子階段重新驗證；不能只因人類回答就跳過必要檢查。
