## 新版流程架構

### 第一階段：工作環境准入

目的：確認目前使用的環境、角色、分支及工作區正確、安全，而且具備開始工作的條件。

1.1 確認 AI 身分與代表角色：老查代表 barry／`collaborator_side`；叉子代表棒子／`owner_side`。雙方均須確認自己是誰、代表誰、能執行哪些操作；不得冒充另一方。

1.2 確認 Repository 與 Supabase 環境：先確認 Repository 正確，再依角色檢查各自可取得的環境證據。老查檢查本機專案及本機可見的 Supabase 快照／migration；叉子以 GitHub 線上 Repository 為根目錄，並在獲授權時直接查核 Supabase。是否需要 Supabase 檢查，必須依本次任務內容判斷：純規格、流程或一般文件任務不需要 Supabase 即時狀態；涉及資料庫結構、正式資料、RLS、RPC、trigger、migration 或 Edge Function 的任務才需要相應證據。不得因為某角色有憑證，就推定另一角色也有。

1.3 確認目前分支與角色分支：雙方都確認目前 branch、HEAD、角色分支、upstream 及工作目錄實際綁定關係；不能只看分支名稱。

1.4 確認 Git 同步與提交關係：fetch 後分別比較本機角色分支與遠端角色分支、`origin/main`；檢查 ahead／behind／diverged、merge-base、提交圖、提交內容及來源。分歧不是永久 BLOCKED 的理由，也不能只因工作區乾淨或技術上可 fast-forward 就放行。必須判斷差異性質並提出可執行處置：一致則通過；單純落後且可安全快轉時依授權同步；本機領先時確認是否為合法角色工作；雙方分歧時分析兩邊提交，再評估 merge、fast-forward、選擇性 cherry-pick、保留分支或要求人類決策。若有衝突，逐檔確認任務歸屬及紀錄權限，不可直接選 ours／theirs。不得丟棄提交、改寫歷史或強制 push。技術上可合併不代表政策上已獲授權。

1.5 確認 Worktree 與工作區安全：列出所有 Worktree、分支、用途、未提交修改、未追蹤檔案、未整合任務及用途不明項目。依情況保留、整合、清理或要求人類決定；不得因為久未活動就刪除，也不得覆蓋唯一檔案或其他任務成果。

1.6 最終准入判定：`READY` 表示必要條件均已確認且可安全開始；`BLOCKED` 表示有已知阻礙，必須說明原因、影響、已做處置及解除條件；`UNKNOWN` 表示缺少無法自行取得的資訊，必須明確指出只有哪位人類／具權限者能提供什麼資料，以及取得後如何驗證。若未知資訊與本次任務無關，應記錄限制，不得把非必要檢查變成永久關卡；若影響安全或正確性，才阻擋相關工作。

### 第二階段：任務辨識與接手

- 只有第一階段 READY 後，才讀取及判斷任務內容。
- 讀取 Board 規範及相關任務完整內容，盤點任務 ID、`from`、`to`、`owner`、`status`、`depends_on`、`branch`、驗收條件及既有紀錄。
- 依 `from` 確認權限歸屬；不得接手、變更或驗收另一方任務。
- 判斷任務是否仍有效、是否已完成、是否有未解除依賴、是否被其他 Worktree 執行，以及目前成果是否已整合。
- 既有任務先確認可接手性，再依 Board 規範留下接手紀錄；不可把新需求開單流程套用到既有任務。

### 第三階段：新需求開單

- 只有確認是新需求、而非既有任務延伸或重複開單時，才建立新任務。
- 先確認開單方及 `from` 權限歸屬，再確認目標、範圍、禁止事項、依賴、驗收條件及必要的人類決策。
- 依 Board 規範檢查根目錄與 archive 的最大任務 ID，避免撞號。
- 建立正式任務檔及 Board 索引，讓任務取得正式 ID。
- 若資訊不足，先完成所有可寫入內容及其他安全檢查，再一次列出缺漏與建議選項；不得逐題打斷。

### 第四階段：建立 Task Branch + Worktree

- 正式任務 ID 取得後，才能建立 `task/T-xxxx-short-name`。
- 從本人最新且乾淨的角色整合分支建立獨立 Worktree；任務分支、Worktree 路徑及 Board `branch` 欄位必須互相對應。
- 先檢查是否已有同 ID 分支／Worktree、來源分支是否安全、是否混入前一任務成果。
- 標準任務分支與 Worktree 依 Board 規範預先授權；非標準分支、跨角色分支或實驗性 Worktree 需另行確認。
- 建立後驗證目前目錄、branch、HEAD、status 及 Worktree 清單，才開始修改。

### 第五階段：開發與驗證

- 依任務範圍實作，不擴張到未授權的檔案、系統或正式環境。
- 每次修改前確認檔案來源、用途及是否有其他任務正在修改。
- 依任務內容選擇必要驗證；測試、瀏覽器、GitHub Pages、Supabase 正式環境及 Edge Function 證據分開記錄。
- 每個子階段先完成安全可行的檢查，再集中提出缺漏與人類決策；不可把未執行的測試寫成通過。
- 修改前後執行 `git diff --check`、`git status --short`，記錄實際命令與 exit code。

### 第六階段：整合與交付

- 先確認任務成果、測試結果、commit、staged files 及禁止 push 範圍。
- 確認任務分支只包含本任務成果，再依 Board 規範整合回本人角色分支。
- Push、PR、部署或正式環境操作仍須符合本次明確授權；本機整合完成不等於遠端已更新。
- 若整合衝突，回到第一階段 1.4 的判斷原則：分析來源、提出建議及人類選項，不可直接丟棄任何一方成果。
- 交付時列出修改內容、commit、測試命令及 exit code、未完成事項、影響任務及實際部署狀態。

### 第七階段：驗收與結案

- 由符合 `from` 權限的角色驗收；需要棒子 Owner 權限或正式帳號的項目，必須由棒子親自確認。
- 逐條核對驗收條件及證據，不得用 AI 自測取代人類專屬驗收。
- 未通過則記錄原因並退回有權限的執行方；有已知阻礙則記錄 `blocked` 及解除條件。
- 全部通過後，依 Board 規範更新 `done_by`、`done_at`、狀態及結案紀錄，再歸檔任務檔。
- 清理任務 Worktree／分支前，確認成果已整合且沒有未提交、未追蹤或唯一副本資料。

## 全流程共通規則：集中彙整後才暫停

1. 每個階段先跑完所有安全可行的子階段檢查，不因第一個缺漏就立即詢問。
2. 每項缺漏先記錄：所在子階段、已知事實、未知內容、影響及是否有安全替代方案。
3. 繼續其他不受影響的唯讀檢查；若後續操作可能覆蓋資料、破壞歷史或造成不可逆影響，立即停止該項操作。
4. 該階段所有可執行子階段完成後，一次列出全部缺漏、異常及待決策事項，再暫停。
5. 人類決策題目使用白話，先給建議選項及理由，再說明其他選項與代價；可有多題，但同一輪集中提出。只有在可靠技術資料仍不足以形成建議時，才中立列出優缺點。
6. 人類補充資訊後，回到受影響子階段重新驗證；不能只因人類回答就跳過必要檢查。
